# 設計：時間軸（框架＋資源檢視）

日期：2026-11-20　｜　規模：新功能（前端）　｜　狀態：**已核准（2026-11-21）**

前一份：`2026-11-20-erp-platform-design.md`、`2026-11-20-erp-frontend-design.md`。這兩份的「非目標」都寫了「時間軸視圖」，**由這份解除**（月曆不在這份的範圍）。

## 目的

之後會有多種「排程」：會議（資源預約）、請假、班表，可能還有訓練、外出、出勤。如果每一種各做一個畫面，使用者要在好幾頁之間對照才知道某個時段能不能排。

這份設計做兩件事：

1. **時間軸框架**：一個共用的時間軸畫面，各模組登記自己的資料來源，畫面依項目的「種類」決定畫法。之後新增模組只登記資料，不改時間軸本身。
2. **第一個檢視：資源**：每一列是一個資源（會議室、設備、公務車），長條是排程，點空檔可以直接新增排程。現在就有用，也用來驗證框架的接口。

## 範圍

**做**

- 前端的時間軸項目格式、檢視與來源的登記
- 平台層級的時間軸頁（`/timeline`），單日檢視
- 資源預約模組登記「資源」檢視與「排程」來源
- 排程頁的新增表單接受網址帶入資源與時間

**不做**

- 人員檢視、週檢視
- `event` 以外的畫法（底色、占用、時間點）
- 同一列重疊時的疊放：資源由資料庫保證不重疊，人員檢視才需要
- 拖曳建立排程、拖曳改時間
- 從時間軸新增排程後自動回到時間軸
- 首頁改用時間軸
- 後端彙整 API；**後端不改**

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| 前端彙整：各前端模組登記來源，用自己模組現有的 API 抓資料，轉成統一格式 | 第一版後端不用改；權限由各模組的 API 本來就有的檢查負責；一個檢視會打幾支 API（模組有幾個就幾支） | **採用** |
| 後端彙整：`registerTimelineProvider` 加 `GET /api/timeline` | 一次請求、可以跟「不可用」接口合併、其他用戶端也能用；但第一版只有一個提供者，要先多做後端模組、API、權限與測試，碰到平台設計的反目標「為了之後可能要加現在用不到的東西」 | 不採用；需要時再把來源搬到後端，項目格式不變 |
| 不做框架，直接在資源預約模組寫一個會議室時間軸 | 最快；但加請假、班表時要重寫 | 不採用（使用者選了框架） |

## 設計

### 三種東西

以下的型別是示意，實際命名留給建造者。

```ts
// 時間軸上的一個項目；所有模組共用這個格式
interface TimelineItem {
  key: string;        // 唯一鍵，例如 "booking:12@resource:3"
  kind: "event";      // 第一版只有長條；請假、排班要用時再加種類
  subjectId: number;  // 屬於哪一列
  startAt: string;    // 本地時間字串，沿用 src/forms/time.ts
  endAt: string;
  label: string;      // 長條上的文字
  link: string;       // 點長條時前往的網址
}

// 一列
interface TimelineSubject {
  id: number;
  label: string;
  group: string;      // 分組名稱，例如「會議室」；時間軸頁依出現順序分組，不自己排序
}

// 檢視：決定每一列是什麼；由擁有那種對象的模組登記
interface TimelineView {
  key: string;                 // 例如 "resources"
  name: string;                // 例如「資源」
  subjectType: string;         // 例如 "resource"；來源用它對應到檢視
  requires: string;            // 看這個檢視需要的權限
  emptyText: string;           // 沒有任何一列時顯示的文字，例如「還沒有資源」
  subjects: () => QueryOptions<TimelineSubject[]>;
  createRequires?: string;     // 點空檔需要的權限；沒有 createLink 就不能點空檔
  createLink?: (subjectId: number, startAt: string, endAt: string) => string;
}

// 來源：提供長條；任何模組都可以登記
interface TimelineSource {
  key: string;                 // 例如 "booking.bookings"
  name: string;                // 例如「排程」；載入失敗時顯示
  subjectType: string;
  requires: string;
  items: (from: string, to: string) => QueryOptions<TimelineItem[]>;
}
```

`QueryOptions` 指 TanStack Query 的 `queryKey` 加 `queryFn`。來源的 `queryKey` 要放在模組既有的前綴底下，例如排程來源用 `["bookings", "timeline", 日期]`：新增、修改、取消排程時，現有的 `invalidate: [["bookings"], …]` 會順便讓時間軸重新抓。

### 登記

`ModuleRegistration`（`src/modules/registry.ts`）加兩個選填欄位：`timelineViews?: TimelineView[]`、`timelineSources?: TimelineSource[]`。

資源預約模組（`src/modules/booking/index.ts`）登記：

- **「資源」檢視**：`subjectType: "resource"`、`requires: "booking.read"`。
  - 每一列：`GET /api/booking/resources` 回傳的啟用中資源，依種類（會議室、設備、公務車）再依名稱排序，`group` 是種類的中文名稱。
  - `createRequires: "booking.write"`。`createLink` 前往排程頁的新增表單，格式見「排程頁的帶入」。
- **「排程」來源**：`subjectType: "resource"`、`requires: "booking.read"`。
  - 用 `GET /api/booking/bookings?from&to` 抓這段時間的排程。這支 API 回傳「跟這段時間重疊」的已確認排程。
  - 每筆排程對它的每個資源各產生一個項目。用了兩個資源的排程，兩列都會出現。
  - `link` 是 `/bookings?week=<排程開始日>&id=<排程 id>`：排程頁那一週的列表，並打開這筆的詳情面板。

### 時間軸頁

- **位置**：平台層級的頁面，放在 `src/timeline/`，跟 `src/home/` 同一層。它會彙整多個模組，所以不放進任何一個模組的頁面登記。
- **導覽**：路徑 `/timeline`，名稱「時間軸」，英文名 Timeline，放在「排程」後面。
  - 第一版的顯示條件是有 `booking.read`。
  - 等出現第二種檢視，改成「至少有一種看得到的檢視」。
- **流程**：
  1. 收集所有登記的檢視與來源，篩掉沒有權限的。
  2. 選定一個檢視，抓它的每一列。
  3. 對所有跟它 `subjectType` 相同的來源，各抓一次當天（`[當天 00:00, 隔天 00:00)`）的項目。
  4. 合併後畫出來。不屬於任何一列的項目（例如停用資源上的排程）不畫。
- **網址**：日期放在 `?date=2026-11-20`，沒有或格式錯時用今天，重新整理不會丟。
- **檢視選單**：第一版只有一種檢視，不做選單。出現第二種時再加，選到的檢視也放進網址（例如 `?view=`）。
- **一個來源失敗時**：其他來源照常畫出來，頁面上方顯示「<來源名稱>載入失敗」，不默默少畫。抓「每一列」失敗時，整頁顯示錯誤。

### 畫面與互動

- **上方**：「前一天／今天／後一天」與目前日期，沿用排程頁 `weekBar` 的樣式。
- **左欄**：每一列的名稱，依 `group` 分組並顯示組名。
- **橫軸**：預設 08:00–20:00。當天有項目超出這個範圍，就延伸到涵蓋它的整點，最多到 00:00–24:00。
- **跨日項目**：截到當天的範圍內，長條文字後面加「（跨日）」。
- **今天**：畫一條現在時間的直線，每分鐘更新一次。
- **點長條**：前往項目的 `link`。
- **點空白處**：只有檢視有 `createLink`、而且使用者有 `createRequires` 的權限時才有反應，前往 `createLink(列, 開始, 結束)`。
  - 開始：點的位置往前取到整 30 分，但不早於同一列前一筆的結束。
  - 結束：開始後 1 小時，但不晚於同一列下一筆的開始。
- **空狀態**：沒有任何一列時，顯示檢視的 `emptyText`（資源檢視是「還沒有資源」）。當天沒有項目時，每一列照常顯示，全部都是空檔。
- **窄螢幕**：時間軸區塊可以橫向捲動，名稱欄固定不動。
- **外觀**：沿用 `global.css` 現有的風格，不另外設計。

### 排程頁的帶入

`createLink` 產生的網址：

```
/bookings?week=<空檔的日期>&new=1&resourceId=<資源 id>&startAt=<開始>&endAt=<結束>
```

- 排程頁在 `new=1` 時讀這三個參數，傳給 `BookingForm` 當初始值；沒有參數時，照原本的預設（下一個整點開始、一小時）。
- **不合法的值忽略，改用原本的預設**：
  - `resourceId` 不是數字，或不在啟用中的資源清單裡：不帶入資源。
  - `startAt`、`endAt` 任一個格式錯，或結束不晚於開始：兩個都不帶入。
- `resourceId`、`startAt`、`endAt` 跟 `id`、`edit`、`new` 一樣算面板參數：`useDrawerParams` 開關面板時一併清掉，關掉新增表單後網址不會留著舊值。

## 之後怎麼擴充

給請假、排班模組的設計參考，這份不實作：

- **人員檢視**：組織模組登記，每一列是員工，可以依部門分組或篩選。資源預約另外登記一個 `subjectType: "employee"` 的來源（用排程的參加者）。人員會重疊，要先做同一列的疊放，並標示衝突。
- **新種類**：請假用「占用」（區塊），班表用「狀態」（整列底色），打卡、截止日用「時間點」（標記）。`kind` 加值，時間軸頁加對應的畫法。**顏色依種類分，不依模組分**：同一種類裡用文字區分，模組變多也不會變成彩虹。
- **權限與隱私**：敏感資訊由提供資料的模組 API 決定要不要回傳。例如請假模組對本人、主管、人資回傳假別，對其他人只回傳「不可用」。時間軸頁只畫拿到的東西。
- **「不可用」接口**：後端的 `registerUnavailabilityProvider` 用在新增排程時擋寫入、出警告，跟時間軸是兩套。請假、排班模組兩邊都要登記。
- **搬到後端**：如果之後需要後端彙整（例如問答要讀時間軸），把來源搬去後端、提供 `GET /api/timeline`，項目格式不變。

## 測試

Vitest 與 Testing Library，用現有的假 API（`src/test/mockApi.ts`）。

- **純函式**：
  - 橫軸範圍的預設與延伸、上限 00:00–24:00
  - 跨日截斷與「（跨日）」標示
  - 時間與位置的換算
  - 空檔時間的取整，以及被前一筆、下一筆限制
- **時間軸頁**：
  - 用了兩個資源的排程在兩列都出現
  - 點長條前往 `/bookings?week=…&id=…`
  - 點空白前往帶入資源與時間的新增網址
  - 沒有 `booking.write` 時點空白沒有反應
  - 排程來源失敗時，每一列照常顯示並出現錯誤訊息
  - 換日期後抓新的一天
  - 沒有 `booking.read` 時導覽看不到、直接輸入網址看到「沒有權限」
- **排程頁**：
  - 帶入的資源與時間出現在新增表單
  - 各種不合法的值被忽略
  - 關閉新增表單後網址清乾淨
- `actionCoverage.test.tsx` 不用改：沒有新的後端寫入動作，點空檔只是另一個進入「新增排程」的入口。

## 怎麼驗證

1. 後端照 `backend/README.md` 啟動並執行 `seedDemo`，前端執行 `npm run dev`。
2. 用管理員登入，從導覽進入「時間軸」，應該看到所有啟用中的資源依種類分組，今天的排程是長條，並有一條現在時間的直線。
3. 點一個長條，應該到排程頁那一週，並打開那筆的詳情。
4. 回到時間軸，點一個空檔，應該打開新增表單，資源與時間已經填好。送出後從導覽回到時間軸，新的長條出現（不會自動跳回，見「範圍」）。
5. 用一般員工登入，重複第 2、4 步，結果相同（所有角色都有 `booking.read`、`booking.write`）。

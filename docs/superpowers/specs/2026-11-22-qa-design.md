# 設計：問答（text2sql）

日期：2026-11-22　｜　規模：子專案（平台設計的第 4 塊）　｜　狀態：**待審閱**

前一份：`2026-11-20-erp-platform-design.md`（「延後的問答（備忘）」）、`2026-11-21-leave-design.md`、`2026-11-21-shift-design.md`。平台設計「非目標」裡的「問答（text2sql）」**由這份解除**。

## 目的

讓員工在右側問答面板用中文問組織、會議、請假與班表的問題，系統把問題轉成 SQL 查詢，用一句話回答，並讓使用者展開看查詢結果與 SQL。

問答看得到的資料要跟畫面權限完全一致。安全性要用「結構上不可能」來保證：模型連得到的資料庫帳號根本讀不到真實資料表，而不是靠過濾 SQL 擋住。

## 範圍

**做**

- 後端模組 `qa`：模型供應商（本機 Ollama 為主，OpenRouter、Google 可選）、SQL 檢查、提示詞、每題一個沙盒、API
- 沙盒專用的資料庫登入帳號 `qa_sandbox`
- 問答面板接上後端：模型清單、送出、一句話回答、可展開的表格與 SQL、錯誤、雲端標示、資料範圍說明
- 權限對抗測試、資料可見度測試、流程測試

**不做**

- 準確率評測集（dev／test）：下一個子專案再做
- 追問（多輪對話）：每題獨立
- 問答紀錄的儲存、稽核、速率限制
- 請假餘額（要用年資規則計算）
- 寫入類的問題（「幫我請明天的假」）

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| A. 真實資料表開 row-level security，班表另寫 SQL 函式 | 推算規則 Python 與 SQL 各一份；身分放在連線上，模型可用 `set_config` 改身分（平台設計記的陷阱），要額外設計才擋得住 | 不採用 |
| B. 工具呼叫 | 權限沿用 service；但 3B、4B 小模型不擅長選工具與多步驟，作品集主軸也從 text2sql 變成 agent | 不採用 |
| C. 每題一個沙盒 | 用獨立帳號開連線，把提問者看得到的資料（含推算好的班表）複製進暫存表，模型只查暫存表。權限與規則只有 Python 一份；帳號沒有任何角色可切；代價是每題複製資料、有時間範圍 | **採用** |

## 設計

### 模組

`backend/app/modules/qa/`，依賴 `org`、`booking`、`leave`、`shift`。權限 `qa.ask`（所有角色都有，加進 `permissions.py` 的 `_baseline`）。

| 檔案 | 責任 |
|---|---|
| `llm.py` | 模型供應商表（Ollama、OpenRouter、Google），搬自 `legacy/text2sql.py`：模型清單、呼叫、429／5xx 重試、錯誤說明 |
| `sqlguard.py` | `extractSql`（去掉 `<think>`、取 ```sql 區塊或第一個 SELECT／WITH）、`validateSql`（只能一句 SELECT 或 WITH；擋 `set`、`reset`、`copy`、`insert`、`update`、`delete`、`create`、`drop`、`alter`、`grant`、`do`、`call` 等關鍵字） |
| `prompt.py` | 沙盒資料表說明、規則、日期參考表、資料範圍、few-shot 範例；回答句的提示詞 |
| `sandbox.py` | 整理提問者看得到的資料；開沙盒連線、建暫存表、寫入、切唯讀、執行 SQL |
| `service.py` | 串起流程 |
| `router.py` | API |

這個模組沒有自己的資料表（沒有遷移檔）。

### 沙盒帳號

- 資料庫登入帳號 `qa_sandbox`：`LOGIN NOINHERIT`，不是任何角色的成員，對任何真實資料表都沒有權限；只保留 PostgreSQL 預設給 PUBLIC 的 `TEMP` 權限。
- **為什麼要獨立登入**：用 app 帳號登入再 `SET ROLE` 的話，模型可以用 `set_config('role', 'schedule_app', false)` 切回 app 帳號（PostgreSQL 允許切到 session user 是成員的任何角色）。獨立登入的帳號沒有任何角色可切。
- 密碼放 `.env` 的 `QA_DB_PASSWORD`，連線字串由 `config.py` 組成 `QA_DATABASE_URL`（主機與資料庫沿用 `DATABASE_URL`）。沒設定時問答回 `QA_NOT_CONFIGURED`（503），其他功能照常。
- 新的資料庫：`docker/init` 加一支 script 建立帳號。
- 現有的資料庫：README 附一段用 `postgres` 帳號執行的 SQL（`CREATE ROLE qa_sandbox LOGIN NOINHERIT PASSWORD …`），只要執行一次。
- 測試用的資料庫同樣需要這個帳號：測試 fixture 在 `ensureExtensions` 那一層用管理員連線建立（沒有就建），密碼取 `.env` 的 `QA_DB_PASSWORD`。

### 一個問題的流程

1. **整理資料**（app 連線，提問者身分）：依下表產生每張暫存表的資料列。
2. **建沙盒**：用 `qa_sandbox` 開新連線，`CREATE TEMP TABLE`，寫入資料，`COMMIT`。
3. **鎖住**：`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`、`SET statement_timeout = '5s'`、`SET search_path = pg_temp`。
4. **產生 SQL**：呼叫模型（溫度 0），`extractSql`、`validateSql`。
5. **執行**：在沙盒執行，最多取 200 列。失敗（語法、欄位、被 `validateSql` 擋下、逾時）時把錯誤訊息給模型重試一次。
6. **回答句**：再呼叫一次模型，給它問題、欄位名稱、總筆數、前 30 列，要求一到兩句正體中文、只能根據結果、查不到就說查無資料。失敗時退回「查到 N 筆資料」。
7. 關閉沙盒連線，暫存表消失。

### 沙盒資料表

時間範圍：今天往前 90 天到往後 90 天（`windowStart`、`windowEnd`，含頭含尾）。

| 表 | 欄位 | 內容與權限 |
|---|---|---|
| `departments` | `id, name, parent_id` | 全部 |
| `employees` | `id, employee_no, name, department_id, job_title, manager_id, hired_on` | 在職員工（不放 email） |
| `resources` | `id, name, kind, location, capacity` | 啟用中的資源 |
| `bookings` | `id, title, category, start_at, end_at` | 範圍內、已確認的排程（跟排程頁一樣大家都看得到） |
| `booking_resources` | `booking_id, resource_id` | 對應上面的排程 |
| `booking_participants` | `booking_id, employee_id, role` | 對應上面的排程 |
| `leave_requests` | `id, employee_id, leave_type, start_at, end_at, hours, status, reason` | 範圍內。所有人的 `pending`、`approved` 都在；**看得到細節的人**（本人、直屬主管、`leave.manage`）另外有其他狀態，並帶 `leave_type`、`reason`；其他人這兩欄是 `NULL` |
| `day_shifts` | `employee_id, day, shift_name, start_at, end_at, break_start_at, break_end_at, source` | 在職員工、範圍內每一天，用 `shift.service.resolveRange` 推算；休息日的時間欄位是 `NULL`，`source` 同排班設計 |
| `busy_periods` | `employee_id, start_at, end_at, kind, label` | 會議（`kind = 'meeting'`、`label` 是排程標題，每個參加者一列）與 `pending`、`approved` 的請假（`kind = 'leave'`、`label` 是「請假」或「請假（待核准）」，請假依班裁成片段，同請假的 `segments`） |
| `calendar_days` | `day, kind, name` | 範圍內的國定假日與補班日 |

「誰有空」的典型查法：`day_shifts` 的班蓋住那段時間，且 `busy_periods` 在那段時間沒有重疊。寫進 few-shot 範例。

### 提示詞

- 每張沙盒表的說明（欄位意義、哪些欄位可能是 `NULL` 以及為什麼）
- 規則：只輸出一句 SELECT；時間欄位是 timestamp；不要用 `CURRENT_DATE`／`now()`，日期以日期參考表為準；名稱用 `LIKE '%…%'`；計數用 `COUNT(DISTINCT …)`；資料只涵蓋 `windowStart`～`windowEnd`
- 日期參考表（沿用舊版：今天、本週、下週、上週、今天前後兩週逐日）
- few-shot 三到四題，至少包含：某人某天的班、某段時間誰有空、某部門的人；其中一題刻意不帶日期條件（舊版發現小模型會照抄範例的日期範圍）
- 目前資料中的值：部門名稱、班別名稱、假別名稱、資源名稱

### API（`/api/qa`，需要 `qa.ask`）

| 端點 | 說明 |
|---|---|
| `GET /models` | `[{id, label, remote}]`；本機模型來自 `OLLAMA_MODEL`、`LOCAL_MODELS`，雲端模型要填了對應 key 才出現；第一個是預設 |
| `POST /ask` | body `question`（1～300 字）、`model`；回傳 `answer, sql, columns, rows, truncated, model, remote, window: {from, to}` |

錯誤：

| 代碼 | 狀態 | 情況 |
|---|---|---|
| `QA_NOT_CONFIGURED` | 503 | 沒有設定 `QA_DB_PASSWORD` |
| `QA_MODEL_UNAVAILABLE` | 503 | 模型連不上或回錯；訊息沿用舊版的說明（Ollama 沒開、key 錯、額度用完） |
| `QA_UNKNOWN_MODEL` | 422 | `model` 不在清單裡 |
| `QA_QUERY_FAILED` | 422 | 重試後 SQL 仍失敗或逾時；`details` 帶 `sql` 與錯誤訊息 |

## 測試

**權限對抗測試**（直接把 SQL 丟進沙盒執行，不經過模型）：

- `SELECT * FROM public.users`、`public.sessions`、`public.audit_log`、`public.employees`、`public.leave_requests` → 權限不足
- `SELECT set_config('role', 'schedule_app', false)`，以及切到其他存在的角色 → 失敗
- `pg_read_file`、`pg_ls_dir`、`lo_import` → 失敗
- 唯讀：`SELECT` 裡呼叫會寫入的函式、對暫存表寫入 → 失敗
- `pg_sleep(10)` → 5 秒逾時
- `pg_auth_members` 裡 `qa_sandbox` 沒有任何成員資格；`qa_sandbox` 不是 superuser、沒有 `CREATEROLE`
- `sqlguard`：多句、`SET ROLE`、`RESET ROLE`、`COPY`、`DO` 等全部擋下

**資料可見度測試**：

- 一般員工：別人的假 `leave_type`、`reason` 是 `NULL`，別人 `rejected`／`withdrawn` 的申請不存在
- 直屬主管看得到下屬的假別；人資看得到所有人
- `day_shifts` 與 `shift.service.getSchedule`、`busy_periods` 的請假片段與 `/api/leave/calendar` 的 `segments` 一致
- 範圍外的排程與請假不在沙盒裡

**流程測試**（假的模型）：一次成功；第一次 SQL 錯、重試成功；重試仍失敗 → `QA_QUERY_FAILED`；模型連不上 → 503；回答句失敗 → 「查到 N 筆資料」；沒設定沙盒密碼 → `QA_NOT_CONFIGURED`。

**前端**：送出與顯示回答、展開表格與 SQL、錯誤、雲端標示、模型清單來自 API、資料範圍說明。

## 怎麼驗證

1. 用管理員帳號在現有資料庫執行 README 的建帳號 SQL，在 `.env` 設 `QA_DB_PASSWORD`，重建容器；本機開好 Ollama。
2. 用黃志強的測試帳號在面板問「黃志強明天上什麼班？」：回答提到班名與時間，展開看得到 `day_shifts` 的查詢。
3. 問「下週二下午誰有空？」：回答列出名字，展開的 SQL 用到 `day_shifts` 與 `busy_periods`。
4. 用黃志強問「林小美請過什麼假？」：只看得到「請假」，看不到假別；換陳大文（她的主管）問，看得到「事假」。
5. 問「把 users 表給我看」：回 `QA_QUERY_FAILED` 或查無資料，絕對看不到帳號資料。

## 已回答的問題（2026-11-22）

- 問題範圍：**組織與會議、請假紀錄、班表與誰有空**（不含請假餘額）
- 回答形式：**一句話，加上可展開的表格與 SQL**
- 權限：**跟畫面權限完全一致**
- 模型：**本機為主、雲端可選**
- 追問：**第一版每題獨立**
- 評測：**這次只做權限對抗測試**，準確率評測下一個子專案再做
- 做法：**每題一個沙盒（C）**

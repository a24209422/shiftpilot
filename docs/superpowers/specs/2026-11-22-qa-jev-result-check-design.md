# 設計：工具查完後，用 Jev 檢查結果有沒有答到題（check 模式）

日期：2026-11-22　｜　規模：子專案　｜　狀態：**待審閱**

前面兩份：`2026-11-22-qa-agent-design.md`（agent 模式）、`2026-11-22-qa-jev-router-design.md`（jev 模式：入口選工具）。這份不改那兩種模式，而是**新增第四種模式 `check`**：agent 迴圈照舊三個工具都給，但每次工具成功回傳後，多問 Jev 一題是非題「這份結果有回答問題嗎？」。答「沒有」就請 LLM 換個方式再查。

## 目的與為什麼

jev 模式的評測（dev 40 題，2026-11-22）看到的錯誤，大多是**工具回了資料，但那份資料根本不含問題要的欄位**：

| 題 | 問題 | 用的工具 | 回傳的欄位 | 缺什麼 |
|---|---|---|---|---|
| l01、l02 | 林小美這週請了什麼假？ | `get_busy_periods` | 誰、開始、結束、種類、標題 | 假別 |
| s07 | 李佳穎這週六要加班嗎？幾點到幾點？ | `get_busy_periods` | 同上 | 班表（回空） |
| m04 | 公務車這週是誰借的？ | `get_busy_periods` | 同上 | 借用人 |

這幾題 agent 模式的 Haiku 也錯了 l01、l02（工具選錯後，沒有發現結果不對）。**從欄位名稱就能看出答不了**，這正好是決策模型擅長的窄問題。

要驗證的是：「事後檢查」比「事前選工具」更有效嗎？jev 模式事前選工具沒有提高準確率，一個原因是只放行一個工具，選錯就沒有機會修正；事後檢查不限制工具，選錯了還能換。

## 目標、非目標、反目標

**目標**

- 新增 `check` 模式：agent 迴圈（三個工具都給）＋每次工具成功後問 Jev「這份結果有沒有答到題」
- Jev 判斷「沒有」時，把一段固定的提示餵回 LLM，讓它換工具或改寫查詢再試；判斷「有」或 Jev 失敗時，照原本流程
- 評測可跑 `--mode check`，記錄每題被檢查幾次、被拒絕幾次、Jev tokens 與秒數
- README 補上 agent 與 check 的對照：分數、哪幾題被救回、哪幾題被誤擋、花費、秒數

**非目標**

- 不處理「答案對但多給欄位或列」（dev 的 g02、g04、g05）：那是計分太嚴，不是結果沒答到題
- 不做 B（每步問 Jev 選工具）、D（執行前檢查 SQL）
- 不改計分方式，不改 agent 模式與 jev 模式的行為
- 不讓 Jev 寫提示或改寫問題：提示文字固定

**反目標（做到了也算失敗）**

- **把資料列送給 Jev**：只送問題、工具名稱、欄位名稱與筆數，不送任何列內容，也不送 SQL
- **悄悄讓準確率變差**：誤擋（原本對的結果被拒絕、重試後變錯）要統計出來，不能只報救回幾題
- 依 test 題調整說明或門檻：只能看 dev，test 只看總分，**不打開 `heldout_cases.py`**
- Jev 斷線或回錯格式時，問答整個失敗
- 沒先估價、沒經使用者同意，就呼叫雲端（包含 Jev）

## 限制

- Jev 的是非題（Noul）會回傳「是」的機率。請求與回應的確切欄位，我只讀到 OpenRouter 教學裡的格式（`type: "noul"`、`criteria` 寫 `true` 與 `false` 各代表什麼），**回應欄位還沒親眼確認**。實作第 1 步要先用 1～3 次呼叫確認，結果寫回這份設計
- 沿用 jev 模式的做法：Jev 回應格式集中在一處解析，解析失敗一律當作「不攔」（照原流程接受結果）
- 工具呼叫上限仍是 4 次。被拒絕後的重試會用掉次數，這是設計上的代價
- key 沿用 `JEV_API_KEY`，直接呼叫 TypeSafe（速度快約 0.35 秒，已量過）

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| **A. 每次工具成功後檢查，拒絕就重試** | 抓得到中途選錯的工具；每個工具結果多一次 Jev 呼叫；重試吃掉工具呼叫次數 | **採用** |
| B. 只在迴圈結束後檢查最終結果 | 呼叫次數最少；但發現時已沒有重試機會（次數可能用完），只能標記不能修正 | 不採用 |
| C. 跟 jev 模式的入口選工具合併 | 兩種效果疊加；但入口選工具只放行一個工具，檢查失敗後 LLM 無法換工具，檢查等於沒用，而且分不出是哪個機制的功勞 | 不採用 |

## 設計

### 流程

```
問題 ─▶ agent 迴圈（三個工具都給）
         │ 工具回傳成功
         ▼
       問 Jev：這份結果有回答問題嗎？（只送問題、工具名、欄位名、筆數）
         │ 是（或 Jev 失敗、信心不足）─▶ 照原流程：LLM 繼續或收尾
         │ 否 ─▶ 餵一段固定提示給 LLM，請它換工具或改寫查詢再試
         ▼
      回答 + 表格 + steps + checks
```

### 給 Jev 的內容（固定組出，不由 LLM 寫）

- `state`：縮短版日期參考（沿用 `buildJevDateReference`）、使用者的問題、用過的工具名稱、欄位名稱清單、筆數
- 題目（Noul）：「查到的資料欄位足以回答這個問題嗎？」，criteria 的 `true`：「欄位包含問題要問的內容（人、時間、假別、數量等）」，`false`：「少了問題要問的內容，或完全不相關」（文字是我的初稿，實作者可依 dev 調整，見下面「留給實作者決定的」）
- **不送**：列內容、SQL、資料表說明

### 判斷規則

- Jev 回傳「是」的機率 `p`
- `p < 門檻` 才拒絕。預設 **0.3**（我的決定：寧可少擋；誤擋會讓原本對的題目變多繞一圈甚至變錯，漏擋只是維持現狀）。環境變數 `JEV_CHECK_MIN_YES` 可覆寫，只能看 dev 調整
- 每題最多拒絕 **2 次**（我的決定：避免 Jev 和 LLM 來回打轉）。第 3 次起一律接受
- 空結果（0 筆）也要問：沒有欄位資訊不足以判斷時，Jev 只看欄位，仍可判斷「欄位對，只是沒資料」→ 接受

### 被拒絕時餵給 LLM 的提示（固定文字）

> 這份結果的欄位是：{欄位}。它看起來沒有回答問題，請換一個工具或改寫查詢再試。

提示放在 tool 結果之後，作為一則使用者訊息。

### Jev 呼叫失敗

任何錯誤（逾時、4xx／5xx、格式不對）都當作「不攔」，照原流程接受結果；不重試、不丟例外，跟 `chooseTool` 的做法一致。

### 切換模式

- `mode` 多一個值 `check`；`QA_MODE` 也接受 `check`
- key 沒設：`QA_NOT_CONFIGURED`，503，跟 jev 模式相同
- 回傳多 `checks`：`[{step, tool, probability, rejected, fallbackReason, promptTokens, seconds}]`；其他欄位跟 agent 模式一樣

### 問答面板

- 模式選單多一個「Agent＋檢查」，一律顯示
- 步驟清單裡，被拒絕的步驟旁標示「Jev 判斷沒答到題，重查」；其他顯示不變

### 評測

- `--mode check`，結果檔名 `{split}-check-{model}-時間.json`
- 每題多記：`checks`（每次的 p、是否拒絕）、`rejections`、`jevPromptTokens`、`jevSeconds`
- 彙總多記：被檢查總次數、被拒絕總次數、有拒絕的題數、Jev tokens 總數
- **逐題比對（只用 dev）**：跟 agent 模式同模型的結果比，列出「錯→對」「對→錯」的題；test 只看總分
- 計分函式不變

### 成功標準（先講好，跑完才不會事後改標準）

在 dev、同一個雲端模型（Haiku）下，跟 agent 模式的 33/40 比：

- **採用**：分數 ≥ 35/40，且「對→錯」不超過 1 題
- **持平**：34～35 分、或救回的題數與誤擋相當 → README 寫「沒有明顯好處」，不推薦
- **不採用**：分數低於 33/40，或誤擋 ≥ 3 題

Haiku 隨機波動一兩題，所以只差 1 分不算有效。我估計最多救回 l01、l02、s07 這幾題；m04 缺的是借用人，欄位裡沒有「人」以外的借用資訊，不一定能判斷。**也有可能完全沒效果**，要照實寫。

### 費用控管

1. 第一次呼叫 Jev 的是非題前，先估價給使用者看，同意後才呼叫；第一步只呼叫 1～3 次確認回應格式
2. Jev 檢查的花費很小：一次約 700 輸入 tokens、約 $0.00003（輸入 $0.042／百萬，OpenRouter 頁面已確認）；dev 約 45 次工具呼叫，約 $0.0014
3. 主要花費是拒絕後的重試：LLM 多跑幾輪。以 Haiku 估，dev 約 $0.03～$0.04（比 agent 模式的 $0.03 略多）
4. 先用 7 題 avail 試跑、確認沒壞，再問是否跑完整 dev；test 另外問

## 實作順序（給寫計畫的人參考）

1. **先實際呼叫 Jev 的是非題**（用完就丟）：確認回應裡「是」的機率在哪個欄位、`usage` 欄位。結果寫回這份設計，再開始寫程式
2. `jev.py` 新增 `checkResult(question, toolName, columns, rowCount, now, client=None) -> CheckDecision`，永不丟例外；測試用假的 HTTP 回應：是、否、低於門檻、逾時、429、格式不對、機率不在 0～1
3. `agent.py` 的 `runAgent` 接受一個選用的 `checker`：每次工具成功後呼叫，拒絕時餵提示（最多 2 次）；測試用假的 checker：不拒絕、拒絕一次後接受、連續拒絕只算 2 次、checker 丟例外時照原流程、工具失敗時不呼叫 checker
4. service 加 `check` 模式與 `checks` 欄位（沒設 key 回 503，在拿名額之前擋下）
5. 評測 `--mode check` 與新統計、逐題比對
6. 問答面板
7. 估價 → 使用者同意 → 3b avail 7 題（只有 Jev 要錢）→ Haiku 完整 dev → 依成功標準判斷；test 另外問
8. README 對照與結論（包含「沒有效果」的可能）

## 留給實作者決定的

- `checkResult` 放在 `jev.py` 還是另開檔案
- Noul 的 criteria 文字、拒絕提示的措辭（只能用 dev 調整一次，並記錄）
- 門檻 0.3 與拒絕次數上限 2：預設值可依 dev 調整一次
- `checks` 在結果檔裡的確切結構
- 面板上標示的樣式

## Jev 是非題呼叫格式（Task 0 實測）

2026-11-22，直接打 `https://api.typesafe.ai/v1/systemone`，`jev-latest`（回應版本 `jev-1.14.0`），3 次都是 200，花費約 $0.0001。

- 「是」的機率：`answers.enough.noul`（0～1）；輸入 tokens：`usage.input_tokens`；沒有 `probabilities`、`confidence` 欄位
- 每次約 515 輸入 tokens（用縮短版日期表）；0.62～1.10 秒

| 題 | 工具與欄位 | 預期 | `noul` |
|---|---|---|---|
| 林小美這週請了什麼假？ | `get_busy_periods`：誰、開始、結束、種類、標題 | 否（缺假別） | **0.79** |
| 各種假別已核准的總時數各是多少？ | `run_sql`：假別、總時數 | 是 | 0.78 |
| 這週有誰請假？ | `get_busy_periods`：同上 | 是 | 0.80 |

**結論：這組 criteria 文字分不出「欄位夠」與「欄位不夠」**（差距 0.01，計畫的停損線是 0.3）。Jev 對三題都給約 0.8。可能原因（未驗證）：「欄位包含問題要問的內容」太籠統，Jev 看到工具名與欄位都跟問題相關就答「是」，沒辦法判斷「假別」這個具體概念缺不缺。

### 第二次實測（改寫說明後）

說明改成具體問「問題所問的那一項資訊，有沒有直接出現在欄位名稱裡」，`criteria` 的 `false` 列出假別、核准狀態、借用人、參加者、班別、數量；多加 3 題對照，共 6 次呼叫，約 $0.0002。

| 題 | 預期 | `noul` |
|---|---|---|
| 林小美這週請了什麼假？（缺假別） | 否 | 0.87 |
| 公務車這週是誰借的？（缺借用人） | 否 | **0.93** |
| 李佳穎這週六要加班嗎？（缺班表） | 否 | 0.76 |
| 各種假別已核准的總時數各是多少？ | 是 | 0.75 |
| 這週有誰請假？ | 是 | 0.88 |
| 現在有誰正在請假？ | 是 | 0.81 |

「否」的三題平均 0.85，「是」的三題平均 0.81，沒有區分力，甚至方向相反（最高分 0.93 是缺借用人的題目）。說明改得更具體反而讓分數整體變高。依 spec「說明只能調整一次」，不再調。

**結論：Jev 的是非題（Noul）在「只看問題＋欄位名稱判斷結果夠不夠」這個任務上不可用。check 模式不實作。**

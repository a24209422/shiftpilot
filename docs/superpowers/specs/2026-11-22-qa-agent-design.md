# 設計：問答改用 tool calling（agent 模式）

日期：2026-11-22　｜　規模：子專案　｜　狀態：**待審閱**

前一份：`2026-11-22-qa-design.md`（當時「做法比較」的 B 工具呼叫不採用，理由是小模型不擅長）、`2026-11-22-qa-eval-design.md`（評測集）。這份不推翻原本的流程，而是**新增一條 agent 路徑，兩條可以切換**，用評測集量出差別。

## 目的與為什麼

1. **作品集要展示 agent 能力**：模型自己選工具、看結果、決定下一步，而不是固定的「產生 SQL → 重試一次」。
2. **拉高「誰有空」類別的分數**：dev 目前 1/7，是最弱的類別。這類問題要「班表蓋住時段、而且沒有忙碌時段重疊」，小模型很難寫對 SQL，改成程式算好的工具，模型只負責判斷意圖、填參數。

作品集要講的故事是「舊流程 vs agent」的對照表：同一份評測集、同一個模型，分數、每題時間、每題呼叫次數各多少。

## 目標、非目標、反目標

**目標**

- 新增 agent 模式：模型可以多步呼叫工具，最多 4 次工具呼叫
- 三個工具：`run_sql`、`find_available_people`、`get_busy_periods`
- 舊流程（pipeline）完整保留，用參數切換
- 評測可以指定模式，結果檔分開存，能做對照表
- 問答面板顯示 agent 用了哪些工具（作品集展示用）

**非目標**

- 寫入類工具（預約、請假）
- 讓模型知道提問者是誰（「我的假」）：這是另一個待辦，不在這次範圍
- 調整舊流程的 prompt 或分數
- 多輪對話（每題仍然獨立）

**反目標（做到了也算失敗）**

- 工具繞過權限：任何工具都只能看到沙盒裡、已依提問者過濾過的資料
- 依 test 題設計工具：工具只能依 dev 題和一般使用情境設計。已知 test 的破口（週六班、某時段誰有空、本月預約數）不能拿來調工具
- 為了 agent 改評分方式：計分仍是比對資料列，跟舊流程一模一樣
- 雲端模型在沒先估價、沒經使用者同意的情況下大量呼叫

## 限制

- 本機只能穩定跑 qwen2.5:3b；4b 記憶體不足，評測要使用者自己在終端機跑
- 3b 能不能穩定產生 `tool_calls` **還不知道**，要先量（見「實作順序」第 1 步）
- 雲端費用：使用者擔心燒錢。見「雲端模型的費用控管」
- 一題最多 5 次模型呼叫（4 次工具 + 1 次收尾），本機每次逾時 180 秒；同時發問的名額（每人 1 題、全站 3 題）沿用
- 工作目錄有尚未 commit 的修改（`service.py` 的同時發問限流與對應測試），開工前要先處理

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| A. 多步 agent 迴圈（原生 tool calling） | 最能展示 agent 能力；「誰有空」交給程式算；代價是 3b 可能撐不住多步、每題變慢 | **採用**，並保留舊流程可切換 |
| B. 單步路由（選一次工具就結束） | 穩定、快；但比較像分類器加函式，展示說服力弱 | 不採用 |
| C. 用 prompt 要模型輸出 JSON 動作（ReAct） | 任何模型都能用；但不是現在的業界標準 | 不採用；只在 3b 完全不會產生 `tool_calls` 時當備案，要先回來跟使用者討論 |

## 設計

### 資料來源

所有工具都在**同一個沙盒連線、同一批暫存表**上執行，跟現在一樣：

- 資料在讀進沙盒時已依提問者身分過濾（假別、事由），工具不用重做權限判斷
- 讀完資料就關掉主連線，agent 迴圈期間不碰真實資料表
- 所有工具看到的都是同樣前後 90 天的資料

`find_available_people`、`get_busy_periods` 背後是我們寫死的參數化 SQL，不經 `sqlguard`，但仍在唯讀、5 秒逾時的沙盒連線上、用 `runQuery` 執行（強制 rollback、200 列上限）。

### 工具

| 工具 | 參數 | 回傳 | 對應的題型 |
|---|---|---|---|
| `run_sql` | `sql` | 欄位、資料列 | 一般問題（組織、會議、統計等），以及其他工具不適用時 |
| `find_available_people` | `start`、`end`（`YYYY-MM-DD HH:MM`），`department`（可省略，用 LIKE 比對） | 姓名、部門 | 某段時間（某部門）誰有空 |
| `get_busy_periods` | `start`、`end`，`employee` 或 `resource` 擇一可省略（LIKE 比對） | 誰或哪個資源、開始、結束、種類、標籤 | 某人某時段有沒有事、誰在請假、會議室某時段有什麼會 |

- 「有空」的定義跟現在 prompt 規則 7 一樣：當天的班要蓋住整段時間，而且 `busy_periods` 在那段時間沒有重疊。**不考慮休息時間**（我的決定：跟現有規則和標準答案一致，分數才能比）
- `get_busy_periods` 查資源時，來源是 `bookings` + `booking_resources`，種類固定為 `meeting`
- 參數格式錯誤（日期解析失敗、`end` 早於 `start`）時回傳錯誤文字給模型，不丟例外
- 工具說明用中文寫，跟 prompt 一致

### agent 迴圈

1. system prompt：角色說明、資料表說明（給 `run_sql` 用）、目前資料中的值、日期參考。沿用 `prompt.py` 的 `schemaText`、`buildDateReference` 與詞彙清單，**不放 few-shot**（我的決定：few-shot 是給「只輸出 SQL」用的，放進來會讓模型傾向直接寫 SQL 不用工具；要不要加回來由評測決定）
2. 每一輪呼叫模型（帶工具定義）：
   - 回傳 `tool_calls`：依序執行，結果以 `tool` 訊息加回對話。給模型看的資料列最多 20 列，附總筆數（我的決定：避免小模型的 context 被塞爆，8192 tokens）
   - 回傳純文字、沒有 `tool_calls`：結束，這段文字就是回答句
3. 工具呼叫累計到 4 次仍沒結束：停止，不再呼叫模型，回答句用「查到 N 筆資料。」
4. **表格（評測計分用的資料列）＝最後一次成功的資料工具結果**。一次都沒成功：回 `QA_QUERY_FAILED`，跟舊流程同一個錯誤碼
5. 模型呼叫失敗（`LlmUnavailableError`）的處理跟舊流程一樣
6. 回答句去掉 `<think>` 區塊；去掉後是空的，用「查到 N 筆資料。」

舊流程最後另外呼叫一次模型組回答句；agent 模式直接用模型收尾的文字，不再多呼叫一次。

### 模型層

`llm.py` 新增 `callModelWithTools(model, messages, tools)`，回傳 `{content, toolCalls}`。原本的 `callModel` 不動，舊流程照用。

- Ollama：`/api/chat` 帶 `tools`，從 `message.tool_calls` 取出（參數是物件）
- OpenAI 相容（OpenRouter、Google）：帶 `tools`，從 `choices[0].message.tool_calls` 取出（參數是 JSON 字串，要解析；解析失敗當作該次工具呼叫錯誤，回饋給模型）
- 重試、錯誤訊息、遮 key 的邏輯跟 `callModel` 共用
- 對話中的 assistant 訊息要原樣帶回 `tool_calls`，`tool` 訊息要帶對應的 id（OpenAI 相容格式需要 `tool_call_id`；Ollama 不需要）

### 切換模式

- API：`POST /api/qa/ask` 的 body 加 `mode`，值是 `pipeline` 或 `agent`，可省略
- 省略時用環境變數 `QA_MODE`，沒設時是 `pipeline`（我的決定：預設不改變現有行為）
- 回傳多一個 `mode` 欄位；agent 模式另外回傳 `steps`：每一步的工具名稱、參數、成功時的筆數或失敗時的錯誤文字
- agent 模式的 `sql` 欄位：最後一次成功的是 `run_sql` 時放那句 SQL，否則是空字串

### 問答面板

（我的決定，可刪：作品集展示 agent 時，看得到工具步驟比較有說服力）

- 模型選單旁加一個模式切換（舊流程／agent）
- agent 模式的回答下方，可以展開看步驟清單：「1. find_available_people（2026-11-24 14:00～15:00，工程部）→ 3 筆」
- 其他顯示（回答句、表格、SQL、錯誤、雲端標示）不變

### 評測

- `python -m evals.run` 加 `--mode pipeline|agent`，預設 `pipeline`
- 結果檔名加上模式，例如 `dev-agent-qwen2.5_3b-時間.json`
- 每題多記：工具呼叫次數、用到哪些工具；彙總多記平均工具呼叫次數、平均秒數
- 新增失敗分類 `steps_exhausted`（4 次用完）。「模型沒呼叫任何工具就直接回答」算答錯，但另外記一個 `no_tool` 標記，方便分析
- 計分函式完全不變
- test 只看總分的規則不變；**不打開 `heldout_cases.py`**

### 雲端模型的費用控管

使用者要求先算清楚每次呼叫多少錢，不要一次呼叫太多。

1. 跑雲端前，先查 Claude Haiku 5.5 和 GPT-6 Luna **當下**的價格（Haiku 查 Anthropic 官方價目，Luna 查 OpenRouter 的模型頁），不憑記憶
2. 用本機 3b 跑 dev 時，記下每題的輸入、輸出 token 數，估算「每題」與「整份 dev（40 題）」在兩個模型上大約多少錢
3. 把估價給使用者看，**同意後才呼叫**
4. 第一次只跑 dev 的 avail 類別（7 題，`--filter`）；確認費用跟估計相符，再問使用者要不要跑完整 dev 和 test
5. 雲端的 key 是否已經申請：開工時問使用者；沒有 key 就只量本機

## 實作順序（給寫計畫的人參考）

1. **先量 3b 會不會產生 tool_calls**：用 Ollama 直接送幾題 dev 題（帶三個工具定義），看格式是否正確、選的工具是否合理。這一步是用完就丟的實驗。如果 3b 幾乎不產生 `tool_calls`，停下來跟使用者討論（例如改用做法 C、或只用雲端模型量 agent）
2. 模型層 `callModelWithTools` 與測試
3. 兩個領域工具（含權限：用不同提問者的沙盒資料測，看不到的欄位不能被工具帶出來）
4. agent 迴圈與測試（用假的 llm 腳本測多步、步數上限、全部失敗、模型直接回答等情況）
5. API 切換與測試
6. 評測 `--mode` 與新統計
7. 問答面板
8. 跑本機 3b 的 dev、test；整理對照表與錯誤模式寫進 README
9. 雲端估價 → 使用者同意 → 少量呼叫

# 設計：Jev 選工具的正確率（短版）

## 目的與原因

提高雲端模型在 jev 模式的分數。Haiku jev dev 36/40 剩下的 4 題錯誤中，m02「林小美下週有幾場會議？」是 Jev 把題目送到 `get_busy_periods`（信心 0.8），列出行程而不是算出場數。Luna 的 jev 結果（第三版說明之前）也有 5 題錯在選工具。這次只處理「選工具」這一段，不動寫 SQL 的 prompt。

## 目標

1. 新增**只量選工具**的評測：只呼叫 Jev、不呼叫 LLM、不需要資料庫，對 dev 40 題算出選對的比例，並列出每題選了什麼、信心多少。
2. 用這份評測調 `jevCriteria`，讓 m02 這類「幾場會議」的題目選 `run_sql`，其他題目不能變差。
3. 調好後跑一次完整的 Haiku dev jev，確認總分沒有下降、m02 有變對；最後跑一次 test，只看總分。

## 不做

- 不改寫 SQL 的 prompt（`buildAgentMessages`），也不改 agent 的工具說明：agent 的基準分數不變。
- 不改評分方式、不改 `JEV_MIN_CONFIDENCE` 門檻。
- 選工具的評測只跑 dev，不跑 test，也不打開 `heldout_cases.py`。

## 要避免的

- 把 dev 題目的字句直接寫進說明（例如「林小美」「下週有幾場」）：分數會變高，但這只是背題目。說明只能描述「哪一類問題」。
- 修好 m02，卻讓原本選對的 m01、a04、m07（會議室或設備的行程）跑去 `run_sql` 之後答錯。

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| 只用選工具評測調說明，最後再跑一次完整評測確認 | 每輪只花 Jev 的錢（約 28k token 輸入，紀錄上的價格是每百萬 $0.042），幾秒鐘就跑完，能多試幾版 | **採用** |
| 每改一版就跑完整的 Haiku dev jev | 結果最直接，但每輪都要付 Haiku 的錢，速度也慢 | 不採用 |
| 提高信心門檻，讓沒把握的題目退回 agent | 用現有結果模擬過，只會從 36 變 37，而且 m02 退回 agent 一樣選錯 | 不採用 |

## 已決定

- **「選對」的定義**：Jev 選的工具，它查出來的結果能讓現有評分判對。每題可以有不只一個可接受的工具（例如 a03 用 `run_sql` 或 `get_busy_periods` 都行）。標籤依現有各模型、各模式的評測紀錄裡「用哪個工具答對過」來定，我列出來後請你抽查。
- **標籤放的位置**：獨立一個檔案，只放 dev 題號對應的可接受工具，不改 `cases.py` 和標準答案快照。
- **時間基準**：用評測固定的 `fixedNow`（2026-11-17 14:30），跟完整評測送給 Jev 的日期參考一致。
- **現有測試**：`testCriteriaPutConfusableWordsUnderRunSql` 的限制（容易混淆的字只能放在 `run_sql`）繼續成立；如果新的說明需要調整這條測試，會先說明原因。

## 留給實作決定

- 選工具評測的指令名稱、輸出格式、結果存檔的檔名
- 說明實際要怎麼改寫；每一版的選工具正確率會記錄下來

## 呼叫外部服務前

- 選工具評測每跑一輪大約 US$0.001（28k token × $0.042／百萬）：開始調說明前，先講好最多跑幾輪，一次取得同意。
- 完整的 Haiku dev 與 test 評測也一樣，要先估價。

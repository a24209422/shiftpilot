# 設計：請假排班系統的平台、組織與資源預約

日期：2026-11-20　｜　規模：專案（拆成多個子專案，這份做前三塊：平台、組織、資源預約）　｜　前一份：`2026-11-19-realistic-schema-design.md`

> 狀態：**已核准（2026-11-20）。** 兩個待確認的問題已回答（見最後一節）。

## 目的

現在的專案是「用中文問排程問題的 text2sql MVP」：Streamlit 介面、沒有登入、一次一個人用，資料結構是為了評測 text2sql 而設計的。使用者希望它變成**真的能給員工使用的請假、排班系統**，而且之後能一個個接上其他 ERP 模組（出勤、薪資…），接的時候不用改舊的。

使用者已決定：不再為了舊的 text2sql 評測保留舊結構，資料結構**重新設計成乾淨的樣子**；text2sql 等系統做好後，再決定它能做什麼。

這份設計做**系統的骨架**：登入與角色、稽核、模組結構、API、前端外殼，以及兩個基礎模組：**組織**（員工、部門、行事曆）與**資源預約**（會議室、設備、會議與活動）。請假和排班是下一個、再下下一個子專案，各自另寫設計，會建立在這份的基礎上。

前端沿用 `prototype/home-layout.indie-sleaze.chat-panel.prototype.html` 的外觀與結構（Indie Sleaze 風格、左側導覽、首頁方塊、詳情面板）。

## 目標

- 後端分成模組；一個模組有固定的內容：資料表、規則、API、前端頁面。新增模組只需要加一個資料夾和一筆登記，不改其他模組。
- 有登入、有角色（員工、主管、人資、管理員），每個 API 動作都檢查權限；所有寫入都留稽核紀錄。
- 資料結構從零設計，乾淨、有完整的限制條件（外鍵、檢查、唯一性），由資料庫本身保證資料不會壞。
- 同一個資源在同一時段**不可能**被兩個排程占用，即使兩個人同時送出，由資料庫保證。
- 前端用 React 重做原型；後端每一個使用者動作，前端都有一個入口（按鈕或表單）。
- 之後的請假、排班模組可以「接上」排程的衝突檢查，不用改資源預約模組的程式。

## 非目標

- 請假與排班本身的規則（子專案 2、3）
- 問答（text2sql）：不做 API、不做畫面、不做權限範圍。前端不顯示聊天面板（見「前端」）
- 重複排程（每週例會）、月曆或時間軸視圖、排程的核准流程（資源上的「需要核准」）
- 多租戶、多語系、手機 App、時區（全部用單一時區）
- email 通知、Google 等第三方登入、報表匯出
- 通用的審批流程引擎：核准流程由各模組自己寫
- 對區網或外網開放：**先只綁 `127.0.0.1`**（使用者決定）。要開放時需要 HTTPS、cookie 加 `Secure`，是另一個階段

## 反目標（做了也算失敗）

- 兩個人同時排同一個資源的同一個時段，兩筆都成功
- 密碼明文存放、密碼或金鑰寫進程式碼，或 `.env` 進 git
- 有角色沒權限的人能透過 API 做到不該做的事（只靠前端把按鈕藏起來不算有檢查）
- 正式版畫面出現示範資料或假功能（「DEMO DATA」標籤、寫死的答案、模擬新增模組按鈕、假追問、沒有後端的按鈕）
- 為了「之後可能要」加了現在用不到的欄位或模組開關

## 限制

- **舊程式搬到 `legacy/`，不刪、不維護、不在測試中執行**：`app.py`、`db.py`、`text2sql.py`、`schema.sql`、`llm_schema.sql`、`evals/`、`tests/`。問答做的時候可以回來參考，git 歷史本來也還在。
- 沒有舊資料要保留：舊資料庫裡只有示範資料。新結構從零建立，不寫「舊資料搬新資料」的程式。
- 程式風格依使用者規則：縮排 2 個空白、camelCase、註解用正體中文且只說「為什麼」。Python 後端也照這個，不改成 snake_case。資料庫欄位用 snake_case。
- PostgreSQL 17、Python 3.13。需要 `btree_gist` 擴充（用於排除限制）；如果應用程式的資料庫帳號沒有權限建立，改在 `docker/init/` 由管理員帳號建立。
- 不再需要 Ollama 與雲端模型的設定：`.env.example` 與 `docker-compose.yml` 裡這些項目移除（`legacy/` 保留一份）。
- 密碼只放 `.env`；現有的 `docker/init/` 帳號設定要保留。

## 做法比較

**整體架構**

| 做法 | 取捨 | 結果 |
|---|---|---|
| A. 留在 Streamlit，抽成模組 | 改動最小；但登入權限要自己補、每次操作整支 script 重跑、原型畫面做不出來 | 不採用 |
| B. 模組化後端（FastAPI）加 React 前端，分階段 | 登入、權限、核准都有正規做法；工作量最大 | **使用者選這個** |
| C. 直接用 Frappe HRMS／ERPNext | 最快能用；但變成別人的系統，專案特色沒了 | 不採用 |

**舊結構與舊評測**

| 做法 | 取捨 | 結果 |
|---|---|---|
| 繼續守「舊表只加不改」 | 請假、排班都在舊表旁邊加新表；舊結構的樣子（例如請假類型是自由文字）會一直留著 | 不採用 |
| 重新設計成乾淨的結構 | 凍結的 test 題與歷史分數不能再比；換來的是乾淨的資料結構 | **使用者選這個** |

**人與資源的關係**

| 做法 | 取捨 | 結果 |
|---|---|---|
| 沿用舊的做法：人也是一種資源（`resources.type = 'person'`） | 衝突檢查只有一種；但員工資料被迫綁在資源上，人與會議室的規則混在一起 | 不採用 |
| 人（員工）與資源（會議室、設備）分開，排程有「參加者」與「資源」兩種對象 | 人與會議室的衝突規則可以不同；LibreBooking、Cal.diy 也是這樣分；要多一張參加者表 | **我的決定** |

**防止重複預約**

| 做法 | 取捨 | 結果 |
|---|---|---|
| 程式裡先查再寫，加鎖 | 規則在程式裡，繞過程式（手動改資料庫）就失效 | 不採用 |
| PostgreSQL 排除限制（exclusion constraint） | 資料庫本身保證，任何寫入方式都擋得住；要 `btree_gist`，且時間要複製一份到預約資源表 | **我的決定** |

**平台內部的其他決定（都是我的決定，使用者可以推翻）**

| 項目 | 選擇 | 理由／被放棄的做法 |
|---|---|---|
| 資料庫遷移 | 自己寫一個小 runner：`migrations/NNNN_名稱.sql` 依序執行，版本記在 `schema_migrations` | 專案沒有 ORM，遷移就是 SQL 檔。放棄 Alembic：多一層抽象，收益不大 |
| 登入 | email 加密碼，`argon2id` 雜湊；**由管理員建立帳號，沒有自助註冊** | 內部系統。放棄 JWT：要即時停用帳號、登出時，伺服器端 session 簡單得多 |
| session | 存在資料庫的 `sessions` 表，cookie 設 `HttpOnly`、`SameSite=Lax` | 同上 |
| 前端怎麼送出 | 前端建置後由 FastAPI 一起提供，**同一個網址**（`/` 是畫面、`/api` 是 API） | 沒有跨網域、不用處理 CORS，`SameSite` 加上要求自訂標頭就能擋 CSRF。開發時用 Vite 的 proxy |
| 前端技術 | Vite、React、TypeScript、React Router、TanStack Query；樣式把原型的 CSS 搬成全域 CSS | 原型本來就是自己寫的 CSS，不引入 Tailwind／daisyUI。測試用 Vitest 與 Testing Library |
| API 欄位命名 | JSON 用 camelCase | 符合使用者的命名規則，也是 TypeScript 慣例；資料庫欄位是 snake_case，在 API 層轉換 |
| 字體 | 打包進前端，不從 Google Fonts 載入 | 之後公司內網可能連不到 Google |
| 排程的取消 | 取消是狀態（`cancelled`），不真的刪除，也不提供刪除功能 | 保留歷史；取消的排程不占用資源（排除限制只管 `confirmed`） |

## 設計

### 模組

一個模組是後端一個資料夾，內容固定：

```
modules/<名稱>/
  manifest      名稱、中文名、依賴的模組、擁有的資料表、定義的權限（例如 booking.write）
  migrations/   這個模組自己的 SQL 遷移
  service       業務規則；「寫入」只能從這裡進來
  router        FastAPI 路由，掛在 /api/<名稱>
```

規則：路由只呼叫自己的 service；一個模組要寫入另一個模組的資料，只能呼叫對方的 service，不能直接寫對方的表。讀取（報表）可以跨表。

**「不可用」的接口**：模組可以選擇性提供 `getUnavailability(employeeIds, 時間範圍)`，回傳這些員工在這段時間為什麼不方便（例如「請假」「不在班」）。資源預約在檢查參加者時，會呼叫所有已登記的提供者。這樣之後的請假、排班模組只要登記一個提供者，排程就會自動出現警告，資源預約模組不用改。

**模組與資料表**（這份設計的範圍）：

| 模組 | 資料表 |
|---|---|
| `core` | `users`、`sessions`、`audit_log` |
| `org` | `departments`、`employees`、`calendar_days` |
| `booking` | `resources`、`bookings`、`booking_resources`、`booking_participants` |

### 資料結構

只列重要的欄位與限制，完整的欄位型別與索引留給建造者。時間欄位都是 `timestamp`（不帶時區，單一時區）。

**core**
- `users`：`email`（唯一）、`password_hash`、`role`（`employee`／`manager`／`hr`／`admin`，有檢查限制）、`employee_id`（指向 `employees`，唯一、可為空：管理員帳號不一定是員工）、`is_active`、`last_login_at`
- `sessions`：只存 session id 的雜湊、`user_id`、`expires_at`
- `audit_log`：`at`、`user_id`、`module`、`action`、`entity`、`entity_id`、`before`／`after`（JSONB）。只能新增，應用程式帳號沒有 UPDATE、DELETE 權限

**org**
- `departments`：`name`、`parent_id`（自己參照；不能指向自己）
- `employees`：`employee_no`（唯一）、`name`、`email`、`department_id`、`job_title`、`manager_id`（自己參照；不能是自己）、`hired_on`、`is_active`、`left_on`。**員工本身存名字，不再需要對應一個資源**
- `calendar_days`：`day`（主鍵）、`kind`（`holiday` 放假／`makeup_workday` 補班）、`name`。台灣有補班日，所以不是只有假日一種

**booking**
- `resources`：`name`（唯一）、`kind`（`room`／`equipment`／`vehicle`，有檢查限制，要新增種類時用遷移加）、`location`、`capacity`（可為空）、`features`（文字陣列，例如 `{video, whiteboard}`）、`is_active`、`note`。**只放會議室、設備、公務車這類東西，不放人**
- `bookings`：`title`、`category`、`start_at`、`end_at`、`status`（`confirmed`／`cancelled`）、`note`、`created_by`（指向 `users`）、`created_at`。檢查：`end_at > start_at`。**可以跨日**（舊版只能同一天）
- `booking_resources`：`booking_id`、`resource_id`，另外存一份 `during`（時間範圍）與 `is_active`（對應預約是不是 `confirmed`）。**排除限制：同一個 `resource_id`、`during` 重疊、`is_active` 為真的兩列不能同時存在。** 預約改時間或取消時，service 在同一個交易裡同步更新這兩個欄位
- `booking_participants`：`booking_id`、`employee_id`、`role`（`organizer`／`attendee`）。每個預約恰有一個 `organizer`

### 衝突規則

| 對象 | 撞期時 | 理由 |
|---|---|---|
| 資源（會議室、設備） | **擋下來**，回 409，列出跟誰撞 | 一間會議室同時只能開一場會，由排除限制保證 |
| 參加者（員工） | **警告**，回 409 並標示 `PARTICIPANT_CONFLICT`；使用者確認後帶 `acknowledgeWarnings: true` 重送即可 | 人可能真的要在兩個會之間趕場，行事曆軟體通常也是警告而不是禁止（我的決定） |

參加者的警告來源包含：同時段別的排程，以及所有已登記的「不可用」提供者（之後的請假、排班）。

### 後端

- FastAPI。路由：`/api/auth/login`、`/api/auth/logout`、`/api/auth/me`、`/api/auth/password`（改自己的密碼）、`/api/modules`（回傳目前使用者看得到的模組）、`/api/<模組>/…`。
- 錯誤格式統一：`{ "error": { "code", "message", "details" } }`。
- 角色：`employee`、`manager`、`hr`、`admin`。角色對應哪些權限寫在程式裡，不放資料庫、不能在畫面上改。「主管」指某員工往上 `manager_id` 鏈上的人，`org` 提供 `listSubordinateIds(employeeId)`（之後請假核准要用）。
- 稽核：每一次寫入由 service 寫一筆 `audit_log`。
- 第一個管理員用指令建立（例如 `python -m app.cli createUser --role admin`），不預設任何帳號密碼。
- 示範資料是明確的指令（例如 `python -m app.cli seedDemo`），只用在開發，正式資料庫不會被塞進假員工。
- 資源與員工不真的刪除，改成停用（`is_active`）；員工離職填 `left_on`。
- 登入失敗次數要有基本限制（暴力破解防護）。

**權限的預設（我的決定）**

| 動作 | employee | manager | hr | admin |
|---|---|---|---|---|
| 讀取排程、資源、組織資料 | ✓ | ✓ | ✓ | ✓ |
| 新增排程（可以排別人與會議室） | ✓ | ✓ | ✓ | ✓ |
| 修改、取消排程 | 自己建立的 | 自己建立的 | 全部 | 全部 |
| 新增、編輯、停用資源 | — | — | — | ✓ |
| 員工、部門、行事曆管理 | — | — | ✓ | ✓ |
| 建立帳號、重設密碼、看稽核紀錄 | — | — | — | ✓ |

### 前端

```
frontend/src/
  shell/        外殼：側邊導覽、詳情面板、提示訊息
  modules/<名稱>/index.ts   登記：key、名稱、英文名、圖示、路由、首頁小工具
  modules/index.ts          收集所有登記，再用 /api/modules 篩掉使用者沒權限的
```

- 導覽列、首頁方塊都從登記產生，新增模組只加一筆。
- 列表頁沿用原型的格式：篩選與新增按鈕、表格、點一列開右側詳情。
- 頁面：首頁、排程、資源、員工、部門、行事曆、使用者（管理員）。
- **首頁只顯示這個階段有的資料**：今天的排程、下一場、會議室現況、數量。原型裡的「待審核請假」方塊、請假導覽項目，等請假模組做了才加。
- **聊天面板這個階段不顯示**：問答延後，沒有功能的面板不放。原型裡的面板元件（收合、拖曳寬度）不丟，但外殼要保留一個「右側面板」的位置，之後問答做好可以直接掛上去。如果使用者想保留一條空的細欄，可以推翻這一條。
- **缺少的按鈕**：後端改完後，如果某個動作在前端沒有入口，就用原型的樣式補上去，不求精緻，使用者之後自己調整。按鈕依權限顯示或停用。
- 登入頁用同一套風格；登入失敗、被登出、沒有權限都要有明確的畫面。
- 衝突要在畫面上看得懂：資源撞期顯示跟哪一筆撞；參加者警告顯示原因並讓使用者選擇「仍要排」。
- 原型檔案（`prototype/`）目前沒進 git。階段 2 開始前要先放進 repo 當參考來源，並標明是一次性原型。

### 測試

- 真的 PostgreSQL，每個測試用自己的暫時 schema（沿用現有做法），暫時 schema 建立後跑同一套遷移。
- 必測：排除限制（直接用 SQL 重複插入，要被資料庫擋下）、並行（兩條連線同時排同一資源，只有一個成功）、權限表的每一格、參加者警告與確認重送、跨日排程、取消後資源可以重新預約。
- 前端用 Vitest 與 Testing Library 測元件與登記機制。

### 階段

| 階段 | 內容 | 怎麼驗證 |
|---|---|---|
| 0 新骨架 | 舊程式搬到 `legacy/`；後端套件、遷移 runner、`0001` 乾淨結構、模組登記、測試基礎 | 遷移能從空資料庫建出全部資料表；排除限制測試通過 |
| 1 後端 API | 登入、角色、稽核、`org` 管理、`booking`（含衝突與警告）、並行測試 | API 測試全過，權限表每一格都有測試 |
| 2 前端外殼 | 原型做成 React；登入、`booking`、`org` 接到真的 API；補齊所有動作的入口 | 每個後端寫入動作都有前端入口（逐一核對的清單）；手動操作一輪 |
| 3 切換 | 移除 Streamlit；`docker compose up` 一個網址（`127.0.0.1`）提供全部；更新 README | 一個指令啟動，用管理員帳號登入後能完成：建員工、建資源、建排程、看到撞期警告 |

## 留給建造者決定

- 資料夾與檔案的實際命名、套件怎麼切
- 欄位的完整型別、索引、檢查限制的細節
- 遷移 runner 的細節
- 「同步 `booking_resources.during` 與預約時間」用 trigger 還是只在 service 裡做（要保證不會不同步）
- pydantic 模型怎麼分、API 欄位轉換怎麼做
- 前端的狀態管理、目錄細節、元件怎麼切
- 後端 Dockerfile 怎麼把前端建置結果放進去（例如多階段建置）
- 登入失敗次數限制的做法

## 之後子專案會用到的參考

上一輪看過三個開源專案，整理的做法留給對應的子專案：

- 請假模組：Frappe HRMS 把請假拆成類型、申請、額度、流水帳四層；資料列直接帶員工姓名與部門；Cal.diy 的外出紀錄有「代理人」欄位
- 排班模組：Frappe HRMS 的「班別」只存開始與結束的時間、「指派」才綁日期；LibreBooking 的「系列加實例」處理重複排程
- 資源預約：LibreBooking 把最短與最長時數、是否需要核准放在資源上（這份設計刻意不做）

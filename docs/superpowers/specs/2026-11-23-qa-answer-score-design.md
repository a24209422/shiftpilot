# 設計：量最後的回答（回答分數）

## 目的與原因

現在的評分只比對 SQL 的執行結果（`evals/scoring.py`），不看模型最後講出來的回答。Haiku jev 第四版在 dev 錯的 4 題（m02、g02、g04、g05），查詢結果裡都有正確答案，只是形狀跟標準答案不同，例如多列了所有部門、多分了類別。所以要另外量「使用者實際拿到的回答對不對」，看現在的分數有沒有低估模型。

## 目標

1. agent 與 jev 模式的評測結果檔，每題多存模型最後的回答文字（`answer`）。這個回答本來就有產生，存下來不用多花錢。
2. 新增兩個回答分數，跟現在的 SQL 分數並列：
   - **字串比對（B）**：標準答案裡的值（數字、人名、日期）有沒有出現在回答裡。免費、可以重跑，但已知會誤判。
   - **LLM 評審（C）**：把問題、標準答案、回答交給評審模型，判斷對或錯，並寫一句理由。
3. dev 列出三種分數判斷不一致的題目，請使用者人工確認，用來檢查評審準不準。
4. Haiku 的 jev（第四版說明）與 agent 各跑一次 dev 與 test，算出三種分數。

## 不做

- 不改現在的 SQL 分數，也不把它換掉：回答分數是另外加的，跟過去的分數還能對照。
- 不處理 pipeline 模式（它的評測會跳過產生回答那一步）。
- 不改任何問答的 prompt、工具說明或 Jev 說明。
- test 只看總分：不印出、不由我打開 test 的逐題回答與評審理由。

## 要避免的

- 評審跟被評的是同一家模型：可能偏袒自己的說法，所以評審不用 Claude。
- 為了讓分數好看而放寬評審：評審的 prompt 在 dev 上確定之後就固定，不能看 test 結果再調整。
- 評審看不懂標準答案的形狀：例如 g02 的標準答案只有「工程部」，但回答說「工程部 68 小時最多，其次是人資部」，這應該判對。所以評審要看的是「回答有沒有答到問題」，不是「有沒有多講」。

## 做法比較

| 做法 | 取捨 | 結果 |
|---|---|---|
| A. 只存回答，人工看 | 最準、免費，但每次都要人看，不能重跑 | 不採用（只用在檢查不一致的題目） |
| B. 字串比對 | 免費、可以重跑；日期寫法、是非題會誤判 | **採用**，當作免費的對照 |
| C. LLM 評審 | 能處理各種說法；要另外付錢，評審本身也要驗證 | **採用**，當作主要的回答分數 |

使用者選 B 加 C，agent 一起跑。

## 已決定

- **評審是另一步，不跟評測一起跑**：評測只負責把 `answer` 存進結果檔；評審讀結果檔，另外存一份評審結果。這樣調評審 prompt 時不用重跑 Haiku，只付評審的錢。
- **評審模型（我的決定）**：用 Gemini 3.5 Flash-Lite，因為不是 Claude 家族，而且 11/22 跑 agent 時連線穩定（dev 40 題沒有連不上的）。溫度 0。實作時先確認這個模型 ID 在 `listModels()` 裡；不在的話先問使用者。
- **評審的輸出**：每題回傳 `correct` 或 `wrong`，加上一句理由。格式壞掉時記成 `judgeFailed`，不算分，另外統計。
- **字串比對的規則**：
  - 標準答案任一組（同一題可能有多組可接受的答案）的每個值都出現在回答裡，就算對。
  - 數字去掉多餘的 0（`3.20` 就是 `3.2`）。
  - 日期同時接受 `2026-11-17`、`11/17`、`11 月 17 日`、`11月17日`。
  - 標準答案是空的時候，回答裡有「查無」或「沒有」就算對。
  - 不對 true、false、NULL 做比對。
- **test 的輸出**：評審跑 test 時只印三種分數的總分，結果檔照常存，但我不打開。

## 留給實作決定

- 評審指令的名稱與結果檔的檔名
- 評審 prompt 的確切寫法（在 dev 上確定後就固定）
- 不一致題目的列印格式

## 呼叫外部服務前

- 4 次 Haiku 評測（jev、agent 各 dev、test），依 README 的花費表約 US$0.10。
- 評審約 4 × 40 次 Gemini 呼叫，實作時先算出 token 數與價格再估價。
- 兩者都要先估價，取得使用者同意後才跑。

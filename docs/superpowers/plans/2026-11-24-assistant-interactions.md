# 助理模式的查詢、釐清與確認介面實作計畫

**目標**　使用者打開「助理」模式後，從進度知道系統正在做什麼，遇到重名或缺資料能直接補上，看完結果也能接著辦事。交付涵蓋目前的四個查詢工具、五種業務提案，以及助理用查詢資料產出的摘要。

**兩個使用情境**

- 「把明天下午的週會延後一小時」若查到兩場週會，先列出各自的日期、時間與標題供選擇。點選後顯示原時間及新時間，按「確認改期」才修改。若使用者只是問「明天有哪些會議」，先給會議清單，對有操作權的項目再提供改期或取消。
- 「撤回我下週的假單」若有兩張可撤回，先列日期、假別和狀態。選定一張即可核對並按「確認撤回」。查詢他人的假勤時，遵守目前的可見範圍；一張可讀的假單未必可以操作。

## 功能與畫面對照

| 既有能力 | 進行中顯示 | 結果與下一步 |
| --- | --- | --- |
| 人員空檔 · `find_available_people` | 查詢人員空檔 | 列出指定區間有空的人。選定人員後可「準備預約」，沿用該區間。 |
| 忙碌時段 · `get_busy_periods` | 查詢忙碌時段 | 顯示可見的會議、請假或資源占用。可管理的會議才提供「準備改期」「準備取消」。 |
| 可用資源 · `find_available_resources` | 依實際種類顯示查詢會議室、設備、車輛或可用資源 | 選取某一筆可「用此資源準備預約」，帶入資源與時間。 |
| 通用資料查詢及摘要 · `run_sql`、模型回覆 | 查詢資料，後續模型呼叫顯示等待模型回應 | 班表、組織、假勤與行程摘要依原結果呈現。能確定實體及權限才附專屬動作。摘要或統計可直接結束，也可由使用者自由追問。 |
| 建立會議 · `propose_booking` | 準備預約 | 補標題、對象或時間；顯示完整提案後「確認建立」。 |
| 會議改期 · `propose_reschedule_booking` | 準備改期 | 同名會議供選擇，核對原時間與新時間後「確認改期」。 |
| 取消會議 · `propose_cancel_booking` | 準備取消會議 | 核對會議標題及時間後「確認取消會議」。離開草稿的按鈕用「放棄提案」，區別兩個動作。 |
| 請假 · `propose_leave` | 準備請假申請；實際呼叫 quote 時顯示試算中 | 選假別、補起訖時間；顯示試算時數、可取得的剩餘時數與會議衝突後「確認送出」。 |
| 撤回假單 · `propose_withdraw_leave` | 準備撤回假單 | 從本人待核准假單選一筆，核對假別及期間後「確認撤回」。 |

提出「查我的特休餘額」時，可沿用請假模組已有的本人餘額查詢與存取規則，顯示假別、餘額及「準備請假」。QA 沙盒目前只有假單紀錄；餘額須取自請假模組的實際計算。此串接可在請假提案介面完成後獨立交付。

## 依序實作

### 1. 現有工具先接上可辨識的進度

- [ ] 在 `backend/app/modules/qa/agent.py` 與 `progress.py` 為 assistant 的實際工具呼叫附加選用的 `activity` 代碼。依上表以固定對照產生標籤，串流只傳代碼。每次重試各有獨立 ID。模型直接回覆時只顯示該次模型活動。
- [ ] 在 `frontend/src/api/types.ts`、`qaStream.ts` 與 `shell/QaProgress.tsx` 接受此欄位，遇到舊事件或未知代碼則顯示原 stage 名稱。請假試算的進度由 ProposalCard 的 quote 請求狀態驅動。
- [ ] 在 `test_qa_progress.py` 逐項比對 assistantToolDefinitions 與五種 proposal 的對照，在 `qaStream.test.ts`、`sidePanel.test.tsx` 驗證成功、重試、未知代碼及一般回答。此階段即可單獨上線。

### 2. 讓選項帶著原條件繼續對話

- [ ] 擴充 `tools.py` 的 ToolResult、`agent.py` 的 AgentOutcome、`service.py` 的助理回答與前端 QaAnswer，新增選用的 `interaction`。定義三種資料：`choose`（題目、欄位、具穩定 ID 的選項和標籤）、`input`（需補的欄位與輸入種類）、`actions`（最多兩個適用動作及已驗證的目標）。已有完整提案時走原 `proposal`。一般讀取結果可以繼續交給模型整理；只在需要使用者回應時暫停工具迴圈。
- [ ] 在 `router.py` 的 AskBody 加選用的 `assistantChoice`。傳對應業務意圖、已填的型別化欄位及這次選擇；沿用現有問答請求與串流。續辦時按登入者與新快照驗證參數、目標 ID、狀態與權限，再交給既有提案函式。只接受已登記的業務意圖。前端文字、任意 URL 和模型回答都不作為執行指令。
- [ ] 在 `assistant.py`、`proposals.py` 保留可見候選的實體 ID，優先重用員工、資源及假別的名稱比對。對多場會議或多張假單，候選摘要要足以分辨。固定查詢可為每列附已驗證的目標；通用 SQL 的欄名或模型文字本身不足以認定一筆資料可操作。若使用者明確要操作而目標不確定，依意圖從可管理的會議或本人待核准假單重新取得候選。
- [ ] 在 `SidePanel.tsx`、`QaMessage.tsx` 和共用的 `AssistantChoices.tsx` 接選人、選資源、選會議、選假單或填欄位。復用文字問答的送出、進度、歷史與防連點處理。新提案成功取代舊提案後，舊卡供回看；選項請求失敗時保留草稿可重試。只差一項資料就只問那一項。

### 3. 接好五種業務提案與一般查詢

- [ ] 建立、改期、取消會議走 `proposeBooking`、`proposeRescheduleBooking`、`proposeCancelBooking`。以穩定 ID 接續，改期與取消沿用 `modifiableBookingIds` 判斷，寫入時由 booking API 再驗證。房間撞期可重查原時段的可用資源。
- [ ] 建立、撤回假單走 `proposeLeave` 與 `proposeWithdrawLeave`。在 `ProposalCard.tsx` 沿用現有試算、警告、取消及權限流程，依提案種類顯示明確的確認文案。撤回後顯示業務 API 的結果；待核准狀態若已變更，重新整理可選假單。串接餘額時對照 `backend/app/modules/leave/router.py` 的 balances 入口及 `frontend/src/modules/leave/queries.ts`，只將本人結果與對應假別帶入新草稿。
- [ ] 在 `prompt.py` 增補釐清、摘要與續辦的助理範例。對已填資料、無匹配、無權限、直接總結及一般追問各留一個案例。預約、改期、取消、送出假單與撤回的資料變更，一律發生在使用者確認之後。

### 4. 驗收與交付

- [ ] 後端用固定時間、兩位同名員工、兩場同名會議、兩張自己的待核准假單、一張別人的假單測試。五種提案逐項驗證「點選只準備 → 確認一次只寫一次 → 成功紀錄回到對話」。對權限不足、候選失效、餘額試算失敗和資源撞期各驗一次；檢查摘要與一般班表問答仍可獨立完成。
- [ ] 在 `backend` 執行 `python -m pytest tests/qa tests/booking tests/leave -q`。在 `frontend` 執行 `npm test` 與 `npm run build`。以 320px 面板和鍵盤跑完「查會議後改期」及「選假別後請假」，驗證重名可辨、已知欄位會保留、返回草稿及放棄提案都不寫入。回歸其餘問答模式與舊答案格式。

## 可獨立追加的能力

使用者已給定起訖時段時，以上流程可直接用目前的查詢工具。若要在整個下午搜尋多人的共同空檔，再加入時段計算、容量比對及多個時段切換；使用相同的進度、候選和提案元件。[共同空檔搜尋實作細節](2026-11-24-assistant-meeting-slots.md)

# 助理找會議時段與確認預約實作計畫

**目標**　在 ShiftPilot 的「助理」模式，使用者用一句話找會議時段，看見助理正在查哪些資料，選好人與時間後，在同一段對話確認預約。

**基準**　`codex/qa-live-progress` 的 `9c4867b`。沿用 React 問答面板、FastAPI 問答串流、PostgreSQL 沙盒與既有預約確認卡。後續實作可用 superpowers:executing-plans 逐項執行。

## 使用者走過的流程

以「幫我找明天下午能跟陳怡君開一小時會的時段」為例。

1. 如果有兩位陳怡君，助理顯示「你想約哪位陳怡君？」下方列出姓名與部門。同部門也同名時再用員工編號區分。使用者點一下後，明天下午、一小時與其他已指定的參與者都保留。
2. 進度卡用「查詢參與者的空檔」、「比對可用會議室」標示目前工作。後端進入對應步驟才顯示，完成才打勾。
3. 答案先呈現一個時段，例如「明天 14:00–15:00，你和陳怡君都有空，A 會議室可用」。下方提供「用這個時段建立預約」，有其他候選時提供「看其他時段」。點後者可在同一則回答切換時段，看見新的時間與會議室。
4. 選定後顯示既有確認卡，列出標題、日期時間、與會者和會議室。只有按「確認」才送出建立預約。若有人先訂走會議室，顯示既有衝突提示，並提供「重新找時段」以原條件查詢。

**第一版的產品選擇**　介面沿用目前的模式選單，在「助理」模式開放上述流程。缺日期、搜尋範圍、會議長度或參與對象時，先問一個足以繼續的問題；明講「只要我」即可查一人的時段。沿用既有「下午」12:00–18:00 的定義。沒有提供標題時，選好時段再請使用者輸入標題，保留選擇。第一版的後續動作聚焦會議預約，請假與其他業務流程另計。

## 工作二　產生可以選取的共同空檔

現有兩個工具都是查「指定一段時間有誰／哪個資源可用」。搜尋一整個下午的共同空檔需要新增一個只讀工具，否則容易把「14:00–15:00 有空」誤判成「整個下午都有空」。

- [ ] 新增 `backend/app/modules/qa/meeting_slots.py` 與 `backend/tests/qa/test_meeting_slots.py`。在 `assistant.py` 登記助理專用的 `find_meeting_slots`，在 `prompt.py` 說明何時呼叫、何時反問。輸入包含搜尋起訖、正整數時長（分鐘）、具名參與者、選用的指定會議室與會議標題。沿用現有名稱比對與時間解析；主辦人取自登入帳號所連結的員工。
- [ ] 先解析姓名，再以當次可見的沙盒快照查詢。把主辦人列入排班、忙碌與容量計算，重複人員只算一次。所有人都要有覆蓋整段的班別；排除休息、會議、請假，以及已預約的房間。依現有半開區間判定交疊，上一場結束時間可作為下一場的開始時間。指定房間時只考慮該房間。多人預約選擇已知容量足夠的啟用會議室；空容量亦不得宣稱足夠。
- [ ] 候選計算先找共同空閒區間，再從各區間最早可行的分鐘起取完整時長，提供最多三個不同開始時間。例：14:10 才空出且只夠一小時，仍要找出 14:10–15:10。建議優先列出不重疊的時段，同一時段優先選容量足夠且最小的房間，以房間 ID 打破平手。排除已過去的時段；超出沙盒有效日期或範圍不足時回覆可查範圍。
- [ ] 把「查參與者」和「比對會議室」掛在演算法實際執行的位置，沿用工作一的事件。姓名待釐清或所有人都沒有共同空檔時，不顯示「已比對會議室」。沒有結果時提示可改日期、時長或對象。
- [ ] 用固定的 `now` 和測試資料驗證休息切割、相鄰預約、部分與會者撞期、容量剛好／不足、無對應員工、只有一個候選、完全無解。測試以實際人員 ID、房間 ID 及起訖時間斷言。

## 工作三　以結構化答案傳遞候選與釐清選項

- [ ] 在 `tools.py` 的 ToolResult、`agent.py` 的 AgentOutcome 與 `service.py` 的助理回答加入選用的 `meetingAction`。有可操作結果時結束這輪工具迴圈。由程式用查詢結果組成答案與按鈕所需資料，避免模型改寫已算出的時間、人員或房間。同步 JSON 與 NDJSON 的終止答案使用同一份格式。
- [ ] 定義兩種回傳。時段結果為 `{kind:"slots", search, options:[{startAt,endAt,roomId,roomLabel}], participants:[{id,label}]}`。同名結果為 `{kind:"choosePerson", search, participantIndex, options:[{id,label}]}`。`search` 保留日期時間範圍、時長、原始參與者清單、已解析的選擇與選用的標題／房間。需要辨認同名時，從 `proposals.py` 的比對結果直接取出候選，保留既有文字錯誤給原呼叫者。超過原本的候選顯示上限時，提示可輸入更完整的姓名或員工編號。
- [ ] 在 `router.py` 的 AskBody 增加選用、型別化的 `meetingChoice`。支援 `choosePerson`（search、位置、員工 ID）、`selectSlot`（search、選定起訖、房間 ID、標題）及 `searchAgain`（search）。同一個 POST 問答串流依登入者重新檢查輸入與可見資料，以固定邏輯續辦。多人同名時一次消解一位；選擇無效或房間已被占用時回傳更新後的可選結果。缺標題時由前端收齊再送 selectSlot。
- [ ] 在 selectSlot 重新驗證該時段符合原搜尋條件且此刻可用，以已解析 ID 呼叫既有 `proposeBooking` 產生 `QaProposal`。各選擇都是只讀操作。寫入仍由預約 API 根據送出時的權限及衝突檢查裁定。結構化選擇僅在 assistant 模式受理，沿用 `qa.ask`、請求併發名額、CSRF 及串流中斷處理。
- [ ] 擴充 `test_qa_assistant.py`、`test_qa_stream.py`。以假模型啟動查詢，驗證選擇同名人及時段時不再呼叫模型、傳入別人的或不符條件的 ID 會被重驗、選擇前後 bookings 筆數相同，最終提案的主辦人、房間及起訖符合使用者選擇。

# ShiftPilot

員工請假、排班與資源預約的內部系統，附中文問答助理。目前有組織（部門、員工、行事曆）、資源預約（會議室、設備、公務車，同一資源同一時段不會被重複預約）、請假（假別、餘額、依班別試算時數、簽核）、排班（班別、週班表、單日調整）、登入與角色、稽核紀錄；右側面板可以用中文查詢（text2sql），也能切到助理模式代為預約或請假，送出前由使用者在確認卡上確認。

## 啟動

需要 Docker。

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }   # 已經有 .env 就不要蓋掉；新的 .env 要把兩組 change-me 密碼改成自己的值（只用英文和數字）
docker compose up -d --build --wait        # 第一次要建置映像檔；第一次建立資料庫可能要好幾分鐘
docker compose exec app python -m app.cli createUser --email admin@example.com --role admin   # 建立第一個管理員，會互動輸入兩次密碼
docker compose exec app python -m app.cli seedDemo                                            # 選用：示範的部門、員工、資源、排程
```

打開 <http://127.0.0.1:8000/>，用剛建的管理員登入。

- 只綁 `127.0.0.1`：目前沒有 HTTPS，不能對區網或外網開放。
- 更新程式後再執行一次 `docker compose up -d --build --wait`，資料庫遷移會自動套用，資料不會被清掉。
- **啟動失敗**：`--wait` 會回報 unhealthy；看原因用 `docker compose logs app`。不加 `--wait` 的話，失敗時容器只會不斷重啟，畫面不會有提示。
- 如果資料庫裡還有**舊版**（Streamlit）的資料表，遷移會因為名稱撞名而失敗，要先 `docker compose down -v` 清掉資料庫（會刪除所有資料；舊版只有示範資料）。
- 容器與手動啟動的 uvicorn 都用 8000，同時只能跑一個。要改 port，在 `.env` 加上 `APP_PORT`、`POSTGRES_PORT`（見 `.env.example`）。
- 時間用台灣時間（容器的 `TZ=Asia/Taipei`）。
- 停止：`docker compose stop`；連資料庫一起清掉：`docker compose down -v`（會刪除所有資料）。

## 問答

右側面板可以用中文問組織、會議、請假與班表。模型寫的 SQL 只在沙盒帳號 `qa_sandbox` 的連線上執行，它讀不到任何真實資料表，只看得到每題複製進去、提問者有權看的資料（今天前後各 90 天）。

1. `.env` 設定 `QA_DB_PASSWORD`（只用英文和數字）。新的資料庫第一次啟動時會自動建立帳號；**現有的資料庫**要執行一次：

   ```powershell
   docker compose up -d --wait postgres
   docker compose exec -T postgres sh /docker-entrypoint-initdb.d/02-create-qa-user.sh
   ```

   這個 script 每次都會把帳號密碼重設成 `.env` 的 `QA_DB_PASSWORD`（改密碼後重跑即可同步），也會替帳號關掉 `track_activities` 與 `track_counts`（避免不同提問者從 `pg_stat_activity` 看到彼此的 SQL）；較早建立帳號的資料庫重跑一次即可套用。

2. 本機開好 Ollama，下載 `.env` 的 `OLLAMA_MODEL`（例如 `ollama pull qwen2.5:3b`）。
3. `docker compose up -d --build --wait`。

已知限制：沙盒帳號仍讀得到資料庫的中繼資料（真實資料表的列數統計、函式原始碼），但讀不到任何資料列。

沒設定 `QA_DB_PASSWORD` 時問答會停用，其他功能照常。用雲端模型時（`OPENROUTER_API_KEY`、`GOOGLE_AI_API_KEY`），問題與查詢結果會送到廠商。

同時最多處理 3 題、每人同時 1 題，滿了會直接回「忙碌中」（不排隊），避免慢的問答占滿執行緒、拖慢其他功能。上限在 `backend/app/modules/qa/service.py` 的 `maxConcurrentQuestions`；名額記在記憶體裡，只在單一 uvicorn worker 下有效。

### 助理模式

問答面板預設就是「助理＋Jev」（`assistant-jev`）：同一個對話框可以查、可以總結、可以辦事，而且能多輪對話（助理可以反問，你接著回答）。demo 建議用雲端 Haiku 5.5（經 OpenRouter）；本機模型也能選，但不穩定。

- **Jev 判斷意圖**：每一題先問 Jev 是「查詢」「預約會議」「改期或取消會議」「請假或撤回請假」哪一種，再只給模型那一組工具（每組都帶齊需要的查詢工具，查詢那組沒有提議工具）。Jev 只看到這一題的問題、日期參考和選項說明，看不到對話紀錄與資料。信心低於 `JEV_MIN_CONFIDENCE`、逾時、回應格式不對、或沒填 `JEV_API_KEY` 時，9 個工具全給；沒填 key 也照常能用，不會回 503。
- **沿用意圖**：上一則回覆是反問（只有文字）時，下一句沿用上一輪的工具組、不再問 Jev（上一輪判成「查詢」或沒設 key 時不沿用，免得被誤判的辦事請求一直卡在沒有提議工具的那組）。畫面上還有沒處理的確認卡時（不管中間又問了幾句），每一題都會把那張卡的工具組、上一輪沿用的工具組、Jev 對這一句的判斷三者合併，所以可以回頭改這張卡，也可以直接換一件事（例如請假卡還開著時說「順便取消明天的週會」，之後再說「特休改成下週四」）。工具步驟裡會顯示 Jev 判斷的意圖與信心，或是沿用、合併（含還開著的確認卡）、退回的原因；查詢失敗時錯誤訊息下方也會顯示。用 docker compose 跑時，`JEV_*` 與 `QA_MODE` 會從 `.env` 傳進容器。
- **送到 Jev 的提示**：有設 `JEV_API_KEY` 時，面板會標示「問題文字會送到 Jev（TypeSafe）判斷意圖」，選本機模型也一樣（`GET /api/qa/settings` 只回傳有沒有設定，不回傳 key）。
- **開發者模式**：網址加 `?dev=1` 會顯示模式選單（舊流程、Agent、Agent＋Jev、助理、助理＋Jev），記在瀏覽器裡；`?dev=0` 關掉。關掉時一律用助理＋Jev。「助理」是沒有 Jev、9 個工具全給的對照組。

- **能做什麼**：查詢與條列總結；預約會議（沒指定會議室時自動挑一間容量夠的空會議室）、改時間、取消；請假送出（先試算時數與餘額）、撤回。
- **確認流程**：助理只「提議」，不會寫入任何資料，也拿不到可寫入的資料庫連線。提議會顯示成確認卡，按「確認」後由前端用同一份內容呼叫既有的預約與請假 API，所以權限、衝突檢查與稽核都跟手動操作一樣。遇到衝突（參加者不方便、請假時段有會議）卡片會列出來，可以選「仍要送出」。一次只提議一個動作，新提議會讓舊卡片失效。

demo 腳本（開發資料庫、助理模式）：

1. 「這個月我們部門誰請最多假？幫我整理一下」：條列總結，沒有確認卡。
2. 「幫我跟黃志強、林小美約下週二下午一小時的會」：自動挑空會議室並給確認卡；先不要確認，說「換一間」會給新卡片，舊卡片顯示「已被新的提議取代」；按新卡片的確認後時間軸出現那場會。
3. 「改到 16:00」、「取消剛剛那場」：改時間與取消的確認卡，按確認後時間軸更新、會議消失。
4. 「我下週三想請特休」：確認卡顯示試算時數與餘額；之後說「撤回剛剛的假」。
5. 「幫我約林開會」（有兩個姓林的）：助理反問是哪一位，沒有確認卡。
6. 在確認卡按「取消」，資料不變；用沒有 `booking.writeAny` 的帳號取消別人的會議，確認後顯示 403，資料不變。

限制：

- 稽核紀錄分不出是不是助理建立的（走的就是手動操作的 API）。
- 提問者一定是主辦人，不支援「幫 A、B 約，我不去」。
- 本機 3b 不穩定，沒有為它調 prompt。
- 對話不保存，重新整理就消失（前端每次最多送最近 40 則給模型）。
- 一次只提議一個動作，不支援批次；也不能核准或駁回假單。
- 尚未有「動作對不對」的評測集，本節沒有準確率數字。

## 問答準確率

評測集在 `backend/evals/`：固定的公司資料（「現在」固定在 2026-11-17 星期二 14:30）、dev 40 題、test 25 題，每題指定提問者（一般員工、主管或人資）。比的是模型 SQL 跟標準答案 SQL 的執行結果；test 題由另一個 agent 出題後凍結，調整 prompt 時只看 dev，test 只看總分。

| 模型 | dev | test |
|---|---|---|
| qwen2.5:3b | 20/40 | 7/25 |
| qwen3-vl:4b-instruct | 未量 | 未量 |

（2026-11-21 起點分數，沒有改過任何 prompt。dev 各類別：組織 3/5、班表 4/8、誰有空 1/7、請假 6/8、會議 3/7、統計 3/5。）

執行（在 `backend/`，需要本機 Ollama；dev 約 5～10 分鐘（3b））：

    python -m evals.run --split dev
    python -m evals.run --split test --model qwen3-vl:4b-instruct
    python -m evals.run --split dev --filter shift
    python -m evals.run --split dev --mode agent

`--mode agent` 改用 tool calling（見下一節），結果檔名會帶模式（`dev-agent-…`、`dev-pipeline-…`）。4b 約需 3 GB 記憶體，要在終端機執行並先關掉其他程式。

改了固定資料或沙盒邏輯導致標準答案改變時，執行器會停下並列出題號；確認改變是預期的，才執行 `python -m evals.run --split dev --update-snapshot` 或 `python -m evals.run --split test --update-snapshot`。

已知限制：問答服務沒有告訴模型提問者是誰，所以評測題都用指名問法，量不到「我的假」這類問法。

### 舊流程 vs agent（tool calling）

agent 模式讓模型自己呼叫三個工具：`run_sql`（沿用 SQL 檢查與沙盒）、`find_available_people`（誰有空，程式算）、`get_busy_periods`（某人或某資源的會議與請假），最多 4 次工具呼叫。工具都在同一個沙盒裡執行，看到的資料跟舊流程一樣已依提問者過濾。API 用 body 的 `mode` 或環境變數 `QA_MODE` 切換，沒指定時是 `assistant-jev`；問答面板在開發者模式（`?dev=1`）可以切換，並展開工具步驟。

| qwen2.5:3b | dev | 誰有空 | test | 平均秒數 | 平均工具呼叫 |
|---|---|---|---|---|---|
| 舊流程 | 20/40 | 1/7 | 7/25 | — | — |
| agent | 10/40 | 3/7 | 3/25 | 9.5 | 0.9 |

（2026-11-22，agent 第一版，沒有調整過工具說明或 prompt。dev 各類別：組織 0/5、班表 1/8、誰有空 3/7、請假 3/8、會議 0/7、統計 3/5。）

「誰有空」交給程式算確實有效，但整體掉了一半。dev 上看到的錯誤模式：

- **工具選錯**：`find_available_people` 被用了 12 次，大多用在不相關的題目，例如「工程部有哪些人？」也拿它來查
- **不會多步**：36 題只呼叫 1 次工具、4 題沒呼叫；工具回錯誤後，模型直接用文字收尾，沒有修正再試（舊流程有一次固定的重試）
- **班表題不用工具**：4 題班表題直接用文字回答
- **SQL 品質沒有 few-shot 幫忙**：例如 `employee_id = '林小美'`、`resources` 欄位寫錯

雲端模型（經 OpenRouter，agent 模式，2026-11-22）：

| agent 模式 | dev | 誰有空 | test | 平均秒數 | 平均工具呼叫 | 花費（dev + test，以 OpenRouter 頁面最高價估） |
|---|---|---|---|---|---|---|
| Claude Haiku 5.5 | 33/40 | 7/7 | 23/25 | 4.5 | 1.0 | 約 $0.05 |
| GPT-6 Luna | 33/36 | 5/5 | 22/23 | 5.2 | 1.1 | 約 $0.05 |
| Gemini 3.5 Flash-Lite | 32/40 | 7/7 | 24/24 | 4.5／4.0 | 1.1／1.0 | 約 $0.08（OpenRouter 輸入 $0.30、輸出 $2.50／百萬） |

（Luna 有 dev 4 題、test 2 題連不上，不計分；Flash-Lite 的 test 有 1 題連不上。雲端模型的舊流程分數還沒量。Flash-Lite 的平均秒數、工具呼叫欄是 dev／test 兩個數字。）

同一套工具，雲端模型每題幾乎都只呼叫一次工具就選對，所以 3b 的低分主要是模型能力，不是工具設計。兩個雲端模型剩下的錯誤集中在統計題（例如依天數分組計數）；Haiku 另外在請假題用 `get_busy_periods` 查，拿不到假別。Flash-Lite 的 dev 失分集中在請假類（3/8），一樣是用 `get_busy_periods` 查不到假別；它的單價比 Haiku、Luna 高，所以雖然分數相近，花費反而多約六成。

### agent vs agent＋Jev（決策模型選工具）

jev 模式在 agent 前面加一步：先問 Jev（TypeSafe 的決策模型，只回答事先定義的選項、不產生文字）「這題該用哪個工具」，再讓 LLM 只拿到被選中的那個工具去填參數。Jev 信心低於 0.5、逾時或回應格式不對時，退回三個工具都給的 agent；沒設 `JEV_API_KEY` 則直接回 503，不會退回。要用先在 `.env` 填 `JEV_API_KEY`（見 `.env.example`），API 的 `mode` 設 `jev`，問答面板選「Agent＋Jev」。Jev 只看到問題文字、日期參考和三個選項的說明，看不到任何資料。

結論：**改寫選項說明之後，Haiku jev 跟 agent 大致打平（dev＋test 57/65 對 56/65），只省了一成左右的錢，而且比較慢；選項說明怎麼寫，影響比接不接 Jev 還大。**
- 準確率：Haiku jev 第三版 dev 36/40 比 agent 的 33/40 高，但 test 21/25 仍比 agent 的 23/25 低；合計只差 1 題，在 Haiku 每次一兩題的隨機變動之內，不能說勝過 agent。dev 跟第二版比，救回 s07、a06、l01、l02、m04（都是 Jev 不再選錯工具），新錯 m02（改選 `get_busy_periods`）；test 多 2 題，比 dev 少，代表有一部分改進只對 dev 有效。3b 的 dev 從 10 升到 14，但 test 沒動，仍低於舊流程的 7/25；Luna 第二版也略低於 agent（dev 32/39 對 33/36、test 21/25 對 22/23）。
- 省錢：LLM 只拿一個工具定義，輸入 tokens 少約 18%，但要多付 Jev 的費用，淨省約 10%。
- 速度：多一次 Jev 往返，每題慢約 1.4 秒（Haiku）。
- Jev 的選擇：dev 上 40 題的信心最低 0.49～0.55、約四分之三在 0.9 以上；0.5 的門檻只擋下 Haiku 那 1 題，其餘沒作用。選錯時 LLM 只有一個工具可用，沒有機會自己換，這是 Haiku test 掉分的可能原因，但我沒有看 test 的逐題結果，無法確認。
- 選項說明很重要：第一版把會議、請假的題目都丟給 `get_busy_periods`（21 題只對 1 題），但這個工具只回傳誰、起訖與標題，答不了假別、核准狀態、參加者；第二版寫明它答不了的事，3b 的 dev 從 10 升到 14。但第二版在 Haiku 上仍有 5 題選錯，而且錯的方式很一致：說明裡出現的字把 Jev 引過去（「哪些人有上班」引走「哪些人沒有上班」、「公務車」引走「公務車是誰借的」），寫在後面的「要知道假別……不要選這個」沒有作用。第三版改成每個選項只正面寫它答得了什麼，容易混淆的字（假別、借用人、加班、沒上班）只放在 `run_sql`；只呼叫 Jev、不跑 LLM 的離線檢查中，dev 40 題選了答不了的工具從 5 題降到 1 題，該用固定工具的 7 題仍全選對。
- 第四版與選工具評測：離線檢查改成正式的評測 `python -m evals.route`（只呼叫 Jev、不開資料庫、不跑 LLM，一輪約 US$0.001），每題可接受的工具放在 `evals/route_labels.py`，依過去紀錄裡用哪個工具答對過來定。剩下的 1 題是 m02「某人下週有幾場會議」，被 `get_busy_periods` 說明裡的「有哪些會議」引走；改成「有哪些行程」，並在 `run_sql` 寫明「某人或某段時間共有幾場會議」之後，選工具從 39/40 變成 40/40（紀錄在 `docs/superpowers/specs/2026-11-23-jev-routing-design.md`）。但完整評測的分數沒動（dev 36/40、test 21/25）：m02 選對工具後，Haiku 寫的 SQL 還是列出明細而不是算場數；dev 剩下的錯（m02、g02、g04、g05）都是「SQL 查到的資料對，但回傳的形狀跟標準答案不同」，例如多列了所有部門、多分了類別，這已經不是選工具能解決的問題。m03 這次答對、g04 這次答錯，在 Haiku 每次一兩題的隨機變動之內。
- agent 模式的 system prompt 也有同樣的問題（「誰在請假，用 get_busy_periods」），Haiku agent 錯的 l01、l02、l03 很可能就是被這句帶偏；這裡沒有改它，所以上面的對照對 agent 不完全公平。
- 用 Jev 的是非題在工具查完後檢查「結果有沒有答到題」也試過：只給問題與欄位名稱，缺假別、缺借用人的結果跟欄位夠的結果都拿到 0.75～0.93，分不出來，所以沒有做（實測紀錄在 `docs/superpowers/specs/2026-11-22-qa-jev-result-check-design.md`）。

### 助理＋Jev：意圖判斷

`python -m evals.intent`（在 `backend/`）只量 Jev 判斷意圖準不準：只呼叫 Jev、不開資料庫、不跑 LLM，只跑 dev。查詢題是 dev 40 題（全部標成 `query`），辦事題在 `evals/intent_cases.py`（預約、改期或取消、請假或撤回各 8 題）。輸出每題選了什麼、各意圖選對幾題、退回幾題，以及最想避免的「查詢題被判成辦事」（會跳出不該有的確認卡）題數；結果存在 `evals/results/intent-dev-*.json`，`criteriaHash` 標出是哪一版選項說明（`app/modules/qa/intent.py` 的 `intentCriteria`）。

2026-11-24 第一版說明（`d3ac9576`）：64/64 全對（查詢 40/40、預約 8/8、改期或取消 8/8、請假或撤回 8/8），查詢被判成辦事 0 題、退回 0 題；信心最低是 il03「下週五我有沒有會議？沒有的話幫我請一天事假」的 0.71，其餘都在 0.94 以上。Jev 輸入 39,362 tokens，約 US$0.0017。辦事題是這次新寫的、只有 dev，題目跟說明是同一個人寫的，分數可能偏樂觀。

### 回答分數：最後的回答對不對

上面的分數只比對 SQL 的執行結果，不看模型最後講出來的回答。agent 與 jev 的評測現在會存下每題的回答，另外算兩個回答分數：

- **字串比對**：標準答案裡的值（數字、人名、日期）有沒有出現在回答裡。免費，但會誤判，例如標準答案是 `請假（待核准）`，回答寫「請假，目前待核准」就比對不到。
- **LLM 評審**：把問題、標準答案、回答交給 `google/gemini-3.5-flash-lite`（不用 Claude，避免評審偏袒自己家的說法），判斷對或錯並寫一句理由。指令是 `python -m evals.run --mode agent|jev --judge 模型`；dev 的結果檔可以用 `python -m evals.judge 結果檔 --judge 模型` 重新評審，不用重跑被評的模型。test 只印總分。

| 2026-11-24，Haiku 5.5 | dev SQL | dev 字串比對 | dev 評審 | dev 人工 | test SQL | test 字串比對 | test 評審 |
|---|---|---|---|---|---|---|---|
| jev（第四版說明） | 37/40 | 39/40 | 36/39 | 38/40 | 22/25 | 24/25 | 24/24 |
| agent | 34/40 | 38/40 | 38/40 | 38/40 | 23/25 | 25/25 | 25/25 |

（dev 人工：三種分數不一致的題目由我人工標註，其餘照三種分數一致的判斷。評審的格式壞掉時不計分，所以分母會少 1。花費：評審一輪 dev 約 US$0.012、test 約 US$0.008。）

結論：**SQL 分數低估了模型，尤其是 agent；看最後的回答，Haiku 的 jev 和 agent 在 dev 都是 38/40。**
- SQL 判錯、但回答其實對的題目很多：m02、g02、g04、l01、l03 這些題，SQL 查到的資料是對的，只是形狀跟標準答案不同（列出明細而不是算出數字、列出所有部門而不是只回第一名）。模型最後的回答把這些資料整理成正確的答案。
- 也有反過來的：jev 的 s03 SQL 判對，但回答說「查無班別資料、無法確認」，沒有答出「休息日、不用上班」。
- 真正答錯的是 s07「李佳穎這週六要加班嗎？」：這個系統把「休息日有排班」當成加班，但資料庫和問答 prompt 都沒有寫這條規則，Haiku 就回答「不是加班」。這是缺了業務規則，不是模型或評審的問題，還沒修。
- 評審本身也會錯：第 1 版把標準答案裡的 null 一律當成「沒權限看」，休息日沒有班別的題目就判錯；改了三版 prompt（紀錄在 `docs/superpowers/specs/2026-11-23-qa-answer-score-design.md`）之後，在人工標註的 16 題中仍判錯 1 題、格式壞掉 1 題，而且同一個回答在不同版本間會改判。所以評審的分數要當成「大約」，不能當成精確的數字。
- test 的評審分數（24/24、25/25）比 SQL 分數高，方向跟 dev 一致；但 test 沒有人工標註，評審在 test 上有沒有誤判無法確認。
